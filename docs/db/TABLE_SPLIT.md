## テーブル

どのテーブルにも、`id`（uuid）、`user_id`（`auth.users` への外部キー。アカウントを消すと一緒に消える）、`created_at`、`updated_at`（サーバーの時刻）を持たせる。RLS は本人の行だけ（`(select auth.uid()) = user_id`）。

| テーブル | 中身 | 参照・制約 |
|---|---|---|
| `settings`（1人1行） | 口座残高・基準日・予算・その他収入・シフトの締め日と給料日・扶養の上限 | 日は1〜31。扶養の上限は `1030000`／`1300000`／`both` |
| `cards` | 名前・締め日・引き落とし日（数値）・並び順・`deleted_at` | 削除済みでないものの中で、名前がユーザー内で重ならない |
| `jobs` | 名前・色・時給・深夜の開始時刻と割増率・交通費・締め日・給料日・並び順・`deleted_at` | 時給は1以上。締め日・給料日は空でもよい（今のコードの既定値を使う） |
| `categories` | 種類（支出／収入）・名前・並び順・`deleted_at` | 種類ごとに、削除済みでないものの中で名前がユーザー内で重ならない |
| `ledger_entries` | 日付・種類・金額・名前・メモ・支払い方法（現金／カード／口座）・並び順 | カテゴリ・カードを ID で参照。カード払いのときだけカードがある。金額は0以上の整数 |
| `shifts` | 日付・開始・終了・時給（その日の時点の値。計算には使わない）・休憩・並び順 | バイト先を ID で参照 |
| `plans` | タイトル・開始日・終了日・開始時刻・終了時刻・予算・完了・メモ・色・並び順 | カードを ID で参照（空でもよい）。終了日は開始日以降。今の `date` は開始日と同じなので持たない |
| `fixed_costs` | 名前・金額・日・種類・支払い方法（口座引き落とし／現金／カード）・並び順 | カードを ID で参照 |
| `fixed_incomes` | 名前・金額・日・並び順 | — （2026-10-31 に `fixed_costs` の収入へまとめ、2026-11-01 に表を消した。D14） |
| `withdrawals` | 日付・金額・並び順 | — |
| `salary_actuals` | 支払月（`pay_month`。今の `salaryKey` の月）・入金日・実額・見込み額 | バイト先を ID で参照。同じバイト先の同じ支払月は1件だけ |
| `card_bill_actuals` | 引き落としの月・実額・見込み額 | カードを ID で参照。同じカードの同じ月は1件だけ |

### 参照先も本人のものであることの保証

外部キーの検査は RLS を通らないので、ID だけの外部キーでは、他人のカードの ID を参照する登録を防げない。そのため次のようにする。

- カード・バイト先・カテゴリに `unique (user_id, id)` を付け、記録からは複合外部キーで参照する（例: `(user_id, card_id) → cards(user_id, id)`）
- カテゴリは `(user_id, category_id, type) → categories(user_id, id, kind)` で参照し、支出の記録に収入のカテゴリを付けられないようにする

### 並び順

- 今の配列の順番は、各テーブルの `position` 列に入れる。読み込みは `position, id` の順
- `created_at` は「テーブルに入れた時刻」とし、架空の登録日時は作らない

## 保存の仕組み

### 手元に持つもの

- **サーバーの写し**: サーバーが保存できたと返した行と、その `updated_at`
- **送信待ち**: まだ送れていない操作の列。端末に保存し、再起動しても残す
- **画面のデータ（`st`）**: サーバーの写しに、送信待ちの操作を重ねたもの

### 操作

- 1回のユーザーの操作（記録の追加、シフトの一括登録、カードの削除など）を1つの「操作」にする。操作には操作 ID を付け、その時点の行の内容をすべて入れて固定する。送っている間に編集しても、送る中身は変わらない
- 操作は1つずつ、DB の関数 `apply_op` を RPC で呼んで送る。1つの操作は1つのトランザクションで、全部保存されるか、全部取り消されるか。別々の API リクエストは共通のトランザクションにならないため
- サーバーは適用した操作 ID を記録する。同じ ID が再送されたら、前回の結果を返す（保存できたのに返事が届かなかった場合の二重保存を防ぐ）
- 成功したら、返ってきた `updated_at` でサーバーの写しを更新し、その操作を送信待ちから外す
- 編集の処理は ID を引き継ぐ。今は家計簿・バイト先・カード・固定費・予定・実績の編集で記録を作り直しているので、すべて直す

### 競合

操作の中の1行でも次に当てはまれば、その操作全体を保存しない。「この端末の内容で上書き」の対象は、競合した行だけ。

| 場面 | 判定 | 「この端末の内容で上書き」を選んだとき |
|---|---|---|
| 別の端末が同じ行を変えた | `updated_at` が違う | その行だけ、今のサーバーの版を基準にして送り直す |
| 別の端末が消した行を編集した | 行がない | その行を作り直す |
| すでに消えている行を消す | 行がない | 成功として扱う |
| 同じ月の給与の実績を2台が新しく登録した | 一意制約 | サーバーにある行を、この端末の値で更新する |

### 送信待ちの保存場所

- キーは `maney:{prod|next}:{ユーザーID}:v2:outbox` のように、本番と試験版・ユーザー・データの形式の版で分ける
- 操作には「どの移行の時点のデータか」の番号を入れ、サーバーは番号の古い操作を受け付けない

### 読み込み

- 全テーブルを、決まった順番で、ページに分けて読む（`.range()`、1ページ500行）。Supabase の取得上限（既定は1,000件）を超えても取りこぼさない
- 件数を一緒に受け取り（`count: 'exact'`）、読んだ行数と一致するかを確かめる
- すべてのテーブルを読み終えて件数が合ったときだけ、サーバーの写しを置き換える。途中で失敗したら前の写しのまま使い、読めなかった行を「削除された」と扱わない
- 置き換えたら、送信待ちの操作を重ね直して画面のデータを作り直す

## 照らし合わせ

- 種類ごとの件数、月ごとの収支の合計、カードごと・バイト先ごとの件数と合計
- **全項目**: 逆の変換（`export_to_user_data`）で「`user_data` → テーブル → JSON」と戻したものが、捨てると決めた項目以外、元と完全に一致すること。合計だけでは、同じ金額の記録同士でカテゴリやメモが入れ替わっても見つからないため
- **画面の数字**: 同じデータを古い版と新しい版の計算に通し、口座残高の推定・引き落とし予定額・給料の見込み・扶養の進み具合が一致すること。時給・深夜割増・交通費をあとから変えたときも比べる（今のデータではシフトの時給とバイト先の時給の違いが0件なので、実データだけでは違いを見つけられない）
- **RLS**: 本人の行だけを読み書きできること。他人のカード・カテゴリの ID を参照する登録が拒否されること

## 戻し方

| 種類 | 方法 |
|---|---|
| 1行だけ戻す | 行の履歴（`private.row_history`）から戻す |
| 1つの操作を取り消す | 履歴に操作 ID と、変更の前と後の行（追加・更新・削除のすべて）を残し、その操作の行をまとめて戻す |
| 全体を、ある時点に戻す | 全テーブルを1つにまとめた写しを、切り替えのときと毎日取り、1つのトランザクションで入れ替える |
| 旧版のアプリに戻す | 逆の変換で `user_data` を作り直す。切り替え後に記録した分もこれで回収できる |

4つとも、③の前に試験データで実際に試す。

## 試験版の分け方

- `next.html` は、localStorage のキーを本番と分ける（`maney-next:` で始める）
- `sw.js` は、`next.html` をキャッシュせず、取得に失敗しても `index.html` を返さないようにする（今の `sw.js` は、取得に失敗するとどのページにも `index.html` を返す）
- 試験が終わったら、移行の番号を上げる。試験版の端末に残った送信待ちは受け付けられなくなる

## 切り替えの手順

1. どの端末にも未送信の変更がないことを確かめる。残っていれば送るか、JSON に書き出して退避する
2. DB のトリガーで `user_data` への書き込みを止める（以降、旧版の保存はエラーになって届かない）
3. 最後のバックアップを取る（DB 内の複製と、手元への JSON）
4. 最後の移行と、全項目の照らし合わせ
5. 「切り替え済み」を記録する。以降、移行の関数は実行を拒否する
6. 新しい版の `index.html` を本番に出す
7. すべての端末で読み込み・保存を確かめる

2〜4 の間に旧版の保存が入り込むことはない（2 のトリガーが DB の中で書き込みを拒否するため）。

新しいユーザー（新しいテーブルに設定の行がない）は、初期値から始め、最初の保存で設定とカテゴリの行ができる。

### 試験の結果（②-4、2026-10-29）

| 試したこと | どこで | 結果 |
|---|---|---|
| 操作（追加・編集・引き出し・シフト2日分・予定・カードの削除） | ローカル（ブラウザ）と本番の試験版 | すべて保存され、読み込み直しても同じ。本番の試験版でも、Google でログインして家計簿の記録を1件保存できた |
| 2台の端末の競合（変更・削除・同じ月の実績） | ローカル（ブラウザと `tests/integration/`） | 競合の通知が出て、「この端末の内容で上書き」「サーバーの内容にする」のどちらも期待どおり |
| 通信できないとき | ローカル（ブラウザ） | 変更が送信待ちに残り、開き直すと送られる（そこで競合も見つかる） |
| 計算の比較 | 本番（読むだけ） | 本番の `user_data` と、新しいテーブルから互換層で作った `st` を同じコードに通し、5つのタブの画面の文字と、口座残高の推定・引き落とし・給料の見込み・扶養の計算がすべて一致した。時給・深夜割増・交通費を変えたときも一致した |
| 4つの戻し方 | 本番（1つのトランザクションで試し、最後に取り消した） | 操作の取り消し・1行だけ戻す・写しから全体を戻す（行の id と登録日時も元のまま）・旧版のアプリに戻す、のすべてで、試す前の内容と一致した |

### 試験版の保存の流れ

1. 画面の処理が `st` を変えて `save()` を呼ぶ（今の画面のコードのまま）
2. 互換層が `st` をテーブルの行に戻し（`stToRows`）、今の行（サーバーの写しに送信待ちを重ねたもの）との違いを、1つの操作にする
3. 操作を送信待ちに入れて端末に保存し、古いものから1つずつ `apply_op` で送る
4. 保存できたら、返ってきた `updated_at` でサーバーの写しを更新する。競合・移し直し・受け付けられなかったときは、送るのを止めて画面で選んでもらう

試験版で記録した内容は、新しいテーブルにだけ入る。本番のアプリ（`user_data`）には出ない。段階③の前に移行し直すと、新しいテーブルは `user_data` の内容で入れ直される（試験版で記録した内容は消える）。

### 実装で決めた細部

設計に書いていない細かい点で、実装のときに決めたもの。

- 列の名前: 日付は `date`、種類は `kind`（`expense`／`income`）、支払い方法は `payment_method`（`cash`／`card`／`bank`）、休憩は `rest_minutes`、予定の日付と時刻は `start_date`・`end_date`・`start_time`・`end_time`
- 予定と固定費の今の数値の `id` は `legacy_id` に残す。逆の変換で元に戻すため
- 給与の実績とカードの実績は、今は1つの配列（`actualInputs`）に混ざって並んでいる。逆の変換で同じ順番に戻せるように、2つのテーブルの `position` は共通の並びにする
- `updated_at` は `clock_timestamp()` で入れる。同じトランザクションの中で2回変えても、毎回新しい値になる
- `created_at`・`updated_at`・`user_id`・`id` はアプリが送った値を使わない（`created_at` と `updated_at` はトリガーが入れ、`user_id` と `id` はあとから変えられない）
- ログインしていない人（`anon`）は、新しいテーブルに一切触れない
- `apply_op` は呼んだ人の権限で動く（security invoker）。RLS がそのまま効くので、他人の行は「ない」ことになる
- 操作の形と結果の形は、マイグレーション（`..._table_split_apply_op.sql`）の先頭に書いた
- 競合の表にない場面: 別の端末が変えた行を消す → 競合（`changed`）。同じ id の行がすでにあるのに追加する → 競合（`exists`）
- 移行の番号は `sync_state.epoch`（行がなければ 1）。番号の確認は再送の確認より先に行う。移行し直したあとに古い操作が再送されても、前回の結果ではなく「番号が古い」を返す
- 保存できた操作の結果（`applied_ops`）は90日で消す。消えたあとに同じ操作が届いても、行がすでにある・`updated_at` が違うので競合になり、二重には保存されない
- 同じユーザーの操作は1つずつ処理する（`pg_advisory_xact_lock`）
- 移行の関数は、今のアプリが作る形だけを受け付け、推測で埋めない。違う形の記録があれば、場所の一覧を出して止まる（`private.find_unmigratable`）
- 一覧（`catExp`・`catInc`）にないが、記録に名前が残っているカテゴリは「削除済み」として作る
- 移行の番号は、初めての移行で 2 にする（行がないときの既定の 1 と区別する）。移行し直すと、そのユーザーの操作の記録（`applied_ops`）も消す
- 逆の変換で、カード・バイト先は削除済みのものも含める（記録が参照しているため。旧版のアプリには「削除済み」がないので、ふつうのカードとして見える）。カテゴリの一覧には削除済みを含めない
- 逆の変換で、新しいアプリで作った予定・固定費の `id` は登録日時（ミリ秒）にする。カードの締め日・引き落とし日と、固定収入の金額・日は、今のアプリと同じく文字列にする
- 試験版の画面: カード・バイト先を削除すると、配列から消さずに削除済みにする（記録のカードの番号がずれない）。削除済みは、選択肢と設定の一覧に出さない（今その記録で選ばれているものは出す）。計算と給与の一覧には使い続け、ホームの引き落としには金額があるときだけ出す
- 試験版の保存: 削除済みのカード・バイト先・カテゴリと同じ名前で追加すると、その行を戻す（名前で参照している記録が、どちらの行か迷わないように）。名前で参照している記録（シフトのバイト先・家計簿のカテゴリ）は、名前が変わっていなければ今の参照のままにする
- 試験版の保存: カード・給与の実績は、`_id` がなくても、同じキー（カードと引き落としの月、バイト先と支払月）の行があればその行の更新にする（一意制約に当たらない）
- 試験版の保存: 記録が参照しているカードが配列から消えたときなど、参照を壊す保存はしない（エラーを出して、変えた内容を取り消す）
- 試験版の保存: 新しい予定・固定費の画面用の `id`（登録日時のミリ秒）は、送る前は端末の時刻、読み込み直すとサーバーの時刻になり、少しずれる。画面では使っていないので問題ない
- 試験版の保存: 送れていない変更があるときにログアウトしようとすると、消えてしまうことを知らせて止める
- 照らし合わせ（`private.compare_migration`）は、全項目の比較に加えて、種類ごとの件数、月ごとの収支、カードごとの件数と合計、バイト先ごとのシフトの件数と時給の合計を比べる
- 戻すとき、行の登録日時は元の値を残し、更新日時はサーバーの今の時刻にする（アプリが「変わった」と気付けるように）
- 1行・1つの操作を戻したときも、それ自体を1つの操作として履歴に残す（戻したのを戻せる）
- 全体の写しは、毎日と、切り替えのとき・全体を戻す直前・手で取ったときに取る。毎日の写しと戻す直前の写しは90日で消し、切り替えのときと手で取った写しは残す
- 全体を戻すときは、行ごとの履歴を残さない（戻す直前の写しで戻せる）
- 旧版のアプリに戻す関数は、`maney.allow_user_data_write = on` にしてから `user_data` に書く。段階③で `user_data` への書き込みを止めるトリガーを入れるとき、これだけは通す
