# DB整備の方針

- 作成日: 2026-10-29
- もとにした資料: [audit-claude.md](audit-claude.md)（2026-10-24）、[audit-codex.md](audit-codex.md)（2026-10-29）
- 状態: **確定**（2026-10-29）。作業はイシューで進める（「方針」の各見出しを参照）

## 2つの診断の比べ方

### 両方が指摘していること

どちらも、いちばんの問題は「保存の仕組み」だという結論だった。

- 全データを1行の JSON で丸ごと上書きするので、2台で使うと片方の変更が消える
- サーバーへの保存を待たず、失敗しても画面に出ない
- カードを「配列の何番目か」で参照しているので、カードを削除すると記録がずれる
- `ledger.amount` が数値と文字列で混ざっている
- 家計簿に同じ内容の記録が27組（余分33件）ある
- DB設定の小さな問題（`ai_insights` に読み取りポリシーがない、`user_id` が NULL を許す、`auth.uid()` が行ごとに評価される、使われていないインデックス、漏洩パスワード保護が無効）
- 使われていないアカウントが3つある
- 進め方: 先に安全策を入れ、そのあとテーブルを分ける

### Claude だけが指摘していること

- **起動時の読み込みに失敗すると、空のデータで全部上書きされうる**。いまのコードでも、`loadRemote()` はエラーを握りつぶし（`index.html:899-926`）、`save()` は読み込みに成功したかを確認せずに全体を送る（`:891-894`）。新しい端末やキャッシュを消した後に起きやすい
- バックアップがない（無料プランには自動バックアップがなく、変更履歴もない）
- 新旧の比較に端末の時計を使っている（`updated_at` もアプリが入れた端末の時刻）
- バイト先・カテゴリを削除すると、記録に名前だけが残る
- 二重持ちのデータ（`plans` の `date` と `dateStart`、`ledger` の `pay` と `cardIdx`）
- 記録ごとの登録日時・更新日時がない。毎回約220KBを全部送っている
- `user_data` のテーブル定義がリポジトリにない（ダッシュボードで作ったため）

### Codex だけが指摘していること

- **給与の実績19件のうち7件に勤務先（`job`）がない**。調べたところ、2026-08-05（`5547bff`）に給与の実績を「月の合計」から「バイト先ごと」に変えたとき、古い7件を変換しなかったのが原因。いまのアプリは勤務先が一致するものしか探さないので（`index.html:1042`）、この7件は画面に出ず、その月は見込みの金額で計算されている
- `ai_insights` を読むときに `user_id` で絞っていない（RLS だけが頼り）。同じ月のアドバイスが重複して入るのを防ぐ制約もない
- GAS がサービスロールで全データを読み、外部AIや LINE に送る設計なので、有効にする前に送る項目と鍵の管理を決める必要がある
- `get_line_userid.gs` の Webhook が LINE の署名を確認していない

### 数字の違い

5日の間に家計簿が16件増えた（1,038件 → 1,054件）。増えた分はすべて文字列の金額（522件 → 538件）だった。手入力の記録は**いまも文字列で保存されている**ので、データだけ数値に直しても、コードを直さないとまた混ざる。

重複の数字は同じで、内訳も一致した。

- 完全に同じ内容の11組（余分11件）: 手入力。二重登録か、本当に2回使ったのかは区別できない
- 取引ID（`txId`）だけが違う16組: カード明細から別々の取引として取り込まれたもの。本当に別の取引の可能性が高い

`merchantRules`・`rakutenCardIdx`・`ledger` の `src` / `txId` は、Codex は「意味が分からない」としていたが、2026-10-24 に削除した楽天カードの取り込み機能（`729f40c`）の名残で、いまは使っていない。

### 優先度の付け方の違い

Codex は `ai_insights` の読み取りポリシーがないことを最優先（P0）にしているが、月次アドバイスはまだ動いていない（GAS が未稼働）。月次アドバイス・LINE通知は使う予定がないので、この方針では対象外にした（下の5）。

## 方針

### 1. まずデータを守る（すぐやる・小さい変更）→ #8

データが消えるのを防ぐ。テーブルの作り直しより先にやる。

- 今のデータのバックアップを取る（JSON を書き出して手元に保存し、DB 内にも複製を作る）
- DB 側で、`user_data` が更新されるたびに古い版を履歴テーブルに残す（トリガー）。アプリを直さなくても、上書きされた後に戻せるようになる
- アプリ側:
  - 起動時の読み込みに成功するまで、サーバーに保存しない
  - 保存の前に、サーバーの `updated_at` が読み込んだ時点から変わっていないかを確かめ、変わっていたら上書きせずに知らせる
  - 保存は順番に1つずつ送り、失敗したら画面に出す

### 2. DB設定を整える（小さい変更）→ #9

- `user_data` のテーブル定義をマイグレーションとしてリポジトリに入れる（いまの状態をそのまま書き起こす）
- `user_id` を NOT NULL にする（NULL の行は0件なので、そのままできる）
- ポリシーを `(select auth.uid()) = user_id` に書き換える

### 3. データを掃除する → #10

- 手入力の金額を数値で保存するようにコードを直してから、文字列の538件を数値に直す
- 給与の実績の古い7件と、使っていない3アカウントをどうするか決める（下の「まだ決めていないこと」）
- 取り込み機能の名残（`merchantRules`・`rakutenCardIdx`）を消す。`src` / `txId` は、テーブルを分けるときに取引IDとして残すか決める
- 手入力の重複11組を確認する

### 4. テーブルを分ける（本格的な作り直し）→ #11

家計簿・カード・バイト先・シフト・予定・カテゴリ・固定費などを別のテーブルにする。各行に ID・登録日時・更新日時を持たせ、参照は ID で行う。カード削除のずれ、名前だけ残る問題、全体の上書き、型の混在がまとめて解消する。アプリの保存処理はほぼ全部書き換えになる。

UI や機能を作る前に DB を整えたい、という目的なので、ここまでやる。ただし1〜3が終わってから始める。

設計と、そこで決めたこと（設定もテーブルにする、`src` / `txId` は捨てる、削除は「削除済み」として残す、4段階で進める など）は [TABLE_SPLIT.md](TABLE_SPLIT.md) にまとめた（2026-10-29 確定）。

### 5. GAS 関連（やらない）

月次アドバイス・LINE通知は使う予定がないので、やらない。使うことになったら、次の点を先に直す。

- `ai_insights` に本人だけが読めるポリシーを追加し、アプリ側でも `user_id` で絞る
- 同じ月のアドバイスが重複しないように、`(user_id, kind, period)` に一意制約を付ける
- 外部AI・LINE に送る項目を最小限にし、鍵の保管方法を決める
- Webhook に LINE の署名の確認を入れる（または、使うときだけ公開する）
- 漏洩パスワード保護を有効にする（いまは Google ログインだけなので実害は小さい）

## 決まったこと（2026-10-29）

1. **テーブルを分けるところまでやる**。1〜3が終わってから始める
2. **月次アドバイス・LINE通知は使わない**。GAS を動かす準備（5）はやらない
3. **手入力の重複11組は確認する**（3の作業の中で、日付と件数の一覧を出して見てもらう）
   - 確認した結果、5組は二重登録だったので1件ずつ消した。6組は別々の記録として残した（#10）
4. **給与の実績の古い7件は消す**（#10 で削除済み）。2026-08-05 より前の「月の合計」の形式で、画面に出ていなかった。その月は見込みの金額で計算されたままになる
5. **使っていない3アカウントは消す**（#10 で削除済み）。どれも初期値のままで、2026-03〜04 に1回ログインしただけだった
