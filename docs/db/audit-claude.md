# maney-app DB診断（Claude）

- 調査日: 2026-10-24
- 調査者: Claude Code（Claude Opus 5.5）
- 対象: Supabase プロジェクト `sgvyjolyfuqchugltvls`（Postgres 17）と、アプリ本体 `index.html` の保存・読み込み処理
- 調査方法: Supabase MCP で、テーブル定義・RLSポリシー・Supabase の診断（security / performance）を取得し、`user_data` の JSON の中身を集計した（読み取りのみで、変更はしていない）。保存処理は `index.html` のコードを読んで確認した

## 結論

データの中身は今のところきれいで、参照切れや壊れた値はなかった。問題は「保存の仕組み」と「データの形」にある。特に保存の仕組みは、**データが丸ごと消えるおそれ**があるので最優先で直したい。

## 現状の構成

### テーブル

| テーブル | 行数 | 内容 |
|---|---|---|
| `user_data` | 4 | `id uuid PK`, `user_id uuid UNIQUE NULL可 → auth.users`, `value jsonb`, `updated_at timestamptz`。アプリの全データを1ユーザー1行の JSON で持つ |
| `ai_insights` | 0 | 月次アドバイス用（GASが書き込む想定。未稼働） |

楽天カード取り込み用の `card_tx` は 2026-10-24 に削除済み（539件すべて家計簿に反映済みだった）。

### RLS ポリシー

- `user_data`: `自分のデータのみ`（ALL, `auth.uid() = user_id`）
- `ai_insights`: RLS は有効だがポリシーなし

### `user_data` の中身（メインのアカウント）

JSON のサイズは約220KB（圧縮後約51KB）。主なキーは次のとおり。

| キー | 件数 | 備考 |

| `ledger`（家計簿） | 1,038 | 2025-07-01〜2026-10-24。支出1,018 / 収入20 |
| `plans`（予定） | 135 | 2026-04-02〜2027-02-14 |
| `shifts`（シフト） | 146 | 2026-03-05〜2026-12-29 |
| `actualInputs`（給与・請求の実績入力） | 28 | |
| `merchantRules`（店名→カテゴリ） | 135 | 取り込み機能の名残。もう使っていない |
| `fixedCosts` / `fixedIncs` / `wds` | 9 / 0 / 14 | 固定費・固定収入・ATM引き出し |
| `jobs` / `cards` | 2 / 3 | バイト先・クレジットカード |

ほかの3アカウントは 2026-03-31〜04-03 に1回ログインしただけで、中身は初期値のまま。

### 保存・読み込みの仕組み（`index.html`）

- `save()` は `saveLocal()`（localStorage）と `saveRemote()` を呼ぶ。`saveRemote()` の完了は待たない
- `saveRemote()` は `st` 全体を `user_data` に upsert する（毎回まるごと上書き）
- `loadRemote()` はアプリ起動時に1回だけ呼ばれる。サーバーの `updated_at` が localStorage の `_updatedAt` より新しいときだけ、サーバーのデータで上書きする

## 問題点

### A. 早めに直したい（データが消える・壊れる）

1. **2台で使うと片方の変更が消える**
   全データを丸ごと上書きし、読み込みは起動時の1回だけなので、iPhone と PC の両方で開いていると、古い画面のまま保存した側がもう一方の変更を全部上書きする。iPhone の PWA は復帰時に読み直さない作りなので起きやすい。新旧の比較には端末の時計を使っているので、端末の時刻がずれていても判定を誤る。

2. **起動時の読み込みに失敗すると、空のデータで上書きされうる**
   新しい端末やキャッシュを消した後に、`loadRemote()` が通信エラーで失敗したまま1件記録すると、初期値＋1件のデータでサーバー上の全データ（約220KB）を上書きする。読み込みに成功したかどうかを保存前に確認していない。

3. **バックアップがない**
   Supabase の無料プランには自動バックアップがなく、データは1行の JSON だけで変更履歴もない。1回の誤上書きで復元できなくなる。

4. **保存の失敗に気づけない**
   `save()` は `saveRemote()` を待たず、失敗してもコンソールに出るだけで画面には出ない。

5. **カードを削除すると記録がずれる**
   カードは「配列の何番目か」の番号で参照されている。`delCard(i)` は `st.cards` から抜くだけで、`ledger[].cardIdx`（933件）・`plans[].planCardIdx`・`actualInputs[].cardIdx` を直さない。固定費の `pay: 'card-N'` も、削除したカードそのものを指すものしか直さない（後ろのカードの番号はずれたまま）。たとえば1枚目を消すと、残りのカードの記録が別のカードとして扱われ、請求額の計算が狂う。

### B. 作り直すときに直したい（データの形）

6. **記録にIDがない**
   `ledger`・`shifts`・`jobs`・`cards` には ID がなく、編集・削除は配列の番号で行っている（`plans` と `fixedCosts` には数値の `id` がある）。完全に同じ内容の記録が27組・余分33件あり、そのうちカード明細由来の16組は別々の取引として取り込まれたもの、手入力の11組（余分11件）は二重登録か本当に2回使ったのかを区別できない。

7. **参照の仕方がバラバラ**
   - カード: `cardIdx` / `planCardIdx`（番号）、`fixedCosts.pay = 'card-0'`（文字列）、`ledger.pay`（カード名）の3通りが混在している
   - バイト先: `shifts.job` / `actualInputs.job` は名前で参照している。名前を変えたときは `saveJobEdit` が追随するが、`delJob` で削除するとシフト側に名前だけ残る
   - カテゴリ: `ledger.cat` は名前で参照している。`delCatExp` / `delCatInc` で削除すると記録側に残る

8. **型が揃っていない**
   - `ledger.amount`: 文字列522件（手入力）／数値516件（取り込み）
   - `cards.closeDay` / `cards.billDay`、`fuyouLimit` が文字列
   - アプリは毎回 `parseInt` で読んでいる

9. **重複・不要なデータ**
   - `plans` の `date` と `dateStart` が全件同じ値（二重持ち）
   - `ledger` の `pay`（カード名）と `cardIdx` の二重持ち
   - 取り込み機能の名残: `merchantRules`（135件）、`rakutenCardIdx`、`ledger` の `src` / `txId`（516件）

10. **記録ごとの登録日時・更新日時がない**
    いつ入力したのかがわからず、変わった分だけを同期することもできない。

11. **毎回の保存で約220KBを全部送っている**
    今は問題ないが、年1,000件ペースで増える。

### C. DB設定の小さな問題

12. `ai_insights` に読み取り許可のポリシーがない。GAS が書き込んでも、アプリからは読めない（Supabase の診断: `rls_enabled_no_policy`）
13. `user_data` のポリシーが `auth.uid()` を行ごとに評価している（診断: `auth_rls_initplan`。`(select auth.uid())` にすべき。今の規模なら影響なし）。`user_id` が NULL を許可している
14. 使われていないアカウントが3つある
15. テーブルをダッシュボードで手作業で作ったため、`user_data` の定義がリポジトリにない（マイグレーション履歴は `drop_card_tx` の1件だけ）
16. `ai_insights_user_kind_idx` が未使用（診断: `unused_index`。機能が未稼働のため）
17. Auth の「漏洩パスワード保護」が無効（診断: `auth_leaked_password_protection`。Google ログインのみなので実害は小さい）

## 良い点（移行しやすい状態）

次の点をチェックし、すべて0件だった。

- `cardIdx` / `planCardIdx` / `actualInputs.cardIdx` の範囲外参照
- `ledger.pay` と `cards[cardIdx].name` の食い違い
- 現在のカテゴリ一覧にないカテゴリ
- 数値にならない金額や、0以下の金額
- `YYYY-MM-DD` 形式でない日付
- 登録されていないバイト先名を持つシフト
- `plans.id` の重複

## 進め方の提案

1. **先に安全策を入れる（小さい変更）**
   - 今のデータのバックアップを取る（DB内に複製テーブルを作る、または JSON を書き出す）
   - 保存の前に「サーバー側の `updated_at` が読み込んだ時点から変わっていないか」を確認し、変わっていたら上書きせずに知らせる
   - 起動時の読み込みに成功するまで、サーバーへの保存をしない
   - 保存の失敗を画面に出す
   - 上書きのたびに旧版を履歴テーブルに残す
   これで A の1〜4はほぼ防げる。

2. **そのあとテーブルを分ける（本格的な作り直し）**
   家計簿・カード・バイト先・シフト・予定・カテゴリ・固定費などを別テーブルにし、各行に ID・登録日時・更新日時を持たせ、参照は ID で行う。1件ずつ保存されるようになり、A の5と B の6〜11も解消する。アプリの保存処理はほぼ全部書き換えになる。
