DB を整えたあと、画面と計算の側（`index.html` など）を監査した。タスク管理を足す前に、今ある要素を整理し、弱点を洗い出すため。

- [audit-codex.md](audit-codex.md): Codex の監査（コードを読んだだけ）
- [../SCREENS.md](../SCREENS.md): 今の画面の構成と遷移（どこを押すとどこに行くか）

## 2つの監査の比べ方

### 両方が指摘していること

- **新しい機能（タスク）を、互換の `st` を通さずに保存する道がない**。Codex はもっと具体的に、`tasks` を `MoneyData.TABLES` に足すだけでは、今の画面で何かを保存するたびに**タスクを全部消す操作ができてしまう**ことを指摘した（確かめた: `diffRows` は全テーブルを比べる。`stToRows` は `tasks` を返さないので、「消えた」と見なされる。`js/data.js:84-96`、`js/compat.js:172-417`）
- お金の計算（残高・カード・給与）が `index.html` の中にあり、テストがない
- 「今日」がアプリを開いた瞬間のまま止まる（`index.html:811-813`）
- 削除に確認も取り消しもない
- 画面はまだ配列の番号や名前で記録を指している。名前などをエスケープせずに `innerHTML` に入れている
- ボタンが `<div onclick>`、入力シートにフォーカスの扱いがない、編集・削除のボタンが小さい
- Service Worker の `CACHE_NAME` を手で上げている
- タスクの置き場所が決まっていない。予定の「完了」とタスクの関係も
- 予定と家計簿の記録がつながっていない。月ごとの推移は「何を支出と数えるか」を先に決める必要がある
- 進め方: 全部を作り直してからではなく、**最小限の土台を作ってからタスク**

### Claude だけが指摘していること

- **お金の数字の決め方が場所ごとにばらばら**。「今日使える」「今月の収支見通し」「残高推移」「状態カード」で、期間と入れるものが違う。現金の支出は残高に入らないのに、現金払いの予定の予算はグラフから引かれる。カード払いの予定は収支見通しで二重に引かれる
- バイト先の締め日が、給料の計算に使われていない（暦の月で計算している）
- 毎月の収入を登録する場所が2つある。「給料サイクル（新規バイト先の初期値）」は、実際は今のバイト先の計算にも使われる
- シフト・固定費・固定収入・ATM の引き出しは編集できない。ATM の日付は必ず今日
- ホームの「今後のイベント・予定」は今月の分だけで、月末になると空になる
- 設定タブの「設定を保存」が約4.7画面下にある。「保存しました」の知らせは、まだ送れていなくても出る
- 削除したカード・バイト先が、カレンダーの締め日などに出続ける
- 扶養の壁（103万・130万）が今の制度と合っているか確かめる必要がある
- アプリに戻ってきたとき、月表示の日の詳細が描き直されず、古いボタンから**別の記録を消しうる**
- 祝日の取得が終わるまで、カレンダーが描かれない
- supabase-js の版を固定していない
- シフトタブ・設定タブが約5画面の長さで、よく使うシフト一覧が奥にある
- アプリ名・画面の構成が「お金管理アプリ」のまま

### Codex だけが指摘していること（主なものは確かめた）

- **月にない日（31日など）**: 固定費などの日が31日だと、30日までの月で `new Date(y, m, 31)` が翌月に繰り越す（`index.html:1375`、`1423-1424`）。確かめたところ、推定残高は翌月1日にずらして数え、残高推移のグラフはその月を飛ばす（`index.html:1403` は日付が一致したときだけ数える）。2つの数字が食い違う
- **日をまたぐシフト**: 22:00〜02:00 のようなシフトは、終わりが始まりより前になるので、給料が0円になる（確かめた: `index.html:1314`）。夜勤をするなら直す。しないなら、入力の時点で防ぐ
- カードを削除すると、そのカード払いの固定費が、知らせずに口座引き落としに変わる（`index.html:1787`）
- 「予算」という言葉が、月の予算と予定の予算の2つの意味で使われている
- ラベルが `for` で入力欄に結び付いていない
- ローカルの Supabase を使う統合テストは、環境変数がないと飛ばされる

### 進め方の違い

| | Claude | Codex |
|---|---|---|
| タスクの前に直すもの | 小さなバグ、画面の構成とお金の数え方を決める、`st` の外を保存する入り口 | `st` の外を保存する入り口、計算の切り出しとテスト、ボタン・入力シートの部品、D1〜D3 |
| お金の計算をまとめる時期 | 「お金の数え方」を決めたあと（タスクのあと） | タスクの前 |
| UI | タスクを新しい作りの最初の1つにする | タスクにも使う部品（ボタン・ダイアログ・44px）を先に整える |

合わせると、次のように分けられる。

- 31日・日をまたぐシフト・「今日」のような**はっきりしたバグ**は、その関数だけテストを付けて先に直す
- 数字の定義が変わる作り直し（お金の計算を1か所にまとめる）は、D11 を決めてからにする
- タスクの画面は、最初から `<button>`・ダイアログ・44px のタップ領域で作る。今ある画面は、あとで1つずつ直す

## 進め方の案（2つを合わせたもの）

| 段階 | やること | 関係する決定 |
|---|---|---|
| 1. すぐ直すバグ | 「今日」が止まる、月にない日、日をまたぐシフト、削除の取り消し、ホームの「今後の予定」の範囲、状態カードの文、削除済みのカード・バイト先の表示。それぞれ小さな PR で、直す関数にはテストを付ける | — |
| 2. 決める | 画面の構成（タスクの置き場所）、お金の数え方、タスクの前に直す範囲、D1〜D3 | D10〜D12、D1〜D3 |
| 3. 土台 | `st` の外のテーブルを読み書きする入り口（タスクが消えないように）、`apply_op` に `tasks` を足すマイグレーション、タスク用の UI 部品 | D4（ファイルの分け方） |
| 4. タスク（最小版） | ROADMAP の Phase 3 | D1〜D3 |
| 5. お金の計算を1か所に | 「お金の出来事」を返す関数を作り、残高・グラフ・見通し・カレンダーはそれを集計する。テストと CI | D11 |
| 6. その先 | 予定と支出、月ごとの推移、通知、ほかの画面を1つずつ新しい作りに移す（Phase 4・6） | D6 |

ROADMAP は今「Phase 2 → 3（タスク）→ 4（ファイルの分割）」の順。この案では、Phase 2 と Phase 4 の一部をタスクの前に移す。順番を変えるかは D12 で決める。
