## 結論

重要な問題は次の5点です。

1. **タスクをそのまま足せる保存経路がない。**  
   `st` を経由しない新機能にする方針は正しいです。しかし今の `save()` は全テーブルの差分を取るため、タスクを追加する前に「`st` 外の行を消さずに保存する」形を作る必要があります。`docs/DECISIONS.md:89`、`js/data.js:84-96`、`js/compat.js:172-417`

2. **残高・カード・給与の計算が画面ファイルに密集し、直接テストされていない。**  
   日付、月末、深夜シフトの境界で壊れやすいです。タスク前にここだけは小さく切り出してテスト可能にすべきです。`index.html:1314-1424`、`docs/ROADMAP.md:23`

3. **画面上の参照が ID ではなく、名前や配列番号に依存している。**  
   カード、バイト先、カテゴリを編集・削除したときの補正コードが増えています。タスクや予定連携を増やすほど、修正漏れの危険が増します。`js/compat.js:73-139`、`js/compat.js:239-317`、`index.html:1787`、`index.html:1937`

4. **iPhone 向けの土台は良いが、操作部品の意味づけが弱い。**  
   `div` をボタンとして使う箇所、狭い削除ボタン、モーダルのフォーカス制御不足があります。タスクは「完了」の頻度が高いので、ここを放置すると使いにくくなります。`index.html:73-88`、`index.html:261-275`、`index.html:284-293`、`index.html:751-767`

5. **本番更新の安全網がまだ手作業に依存している。**  
   main が本番で、Service Worker のキャッシュ名も手で更新する運用です。タスク実装前に全面 CI は不要ですが、計算テストとキャッシュ更新の事故は減らすべきです。`docs/GIT_WORKFLOW.md:5-6`、`docs/GIT_WORKFLOW.md:57`、`sw.js:1-24`

良い点もあります。DB 側への保存を `js/data.js` に寄せ、送信待ち、再送、競合、サーバー版採用を考慮している点は堅実です。互換層を「移行用」と明記している判断も適切です。`js/data.js:39-44`、`js/data.js:97-242`、`docs/db/SCHEMA.md:148-166`

## 進め方の提案

**全面的な内部設計の作り直しや Vite 化を、タスク管理より先に終える必要はありません。**  
ただし、**タスク実装の前に最低限の内部設計と UI の修正は必要**です。

先にやる範囲は、次の4つに絞るべきです。

1. **`st` 外のテーブルを安全に保存できる形にする。**  
   これが最優先です。tasks を `TABLES` に足すだけでは既存保存時に削除扱いになる危険があります。タスクは新しいテーブルとして扱い、互換 `st` の保存結果と直接モデルの行を合成して差分化します。`js/data.js:84-96`、`js/compat.js:172-417`

2. **日付・給与・カード・残高の計算だけを純粋関数へ切り出し、境界テストを書く。**  
   全画面の分割は後回しでよいです。少なくとも月末、31日、深夜跨ぎ、カード締め日前後、基準日、実績入力済みのケースを守ります。`index.html:1314-1424`

3. **タスクにも使う最低限の UI 部品を先に整える。**  
   ボタン化、選択状態、モーダルのフォーカス、44px程度のタップ領域を共通化します。既存の全画面を直し切る必要はありません。`index.html:261-293`、`index.html:751-767`

4. **D1〜D3 を決める。**  
   特に保存先と予定との関係を決めないまま画面から作り始めないことです。`docs/DECISIONS.md:3-24`

その後に、タスク MVP を小さく実装するのがよいです。  
逆に、ファイル全分割、TypeScript 化、全 UI の再設計、通知基盤、予定と支出の連携まで待つ必要はありません。それらは Phase 4 以降の大きな改善として進めるべきです。`docs/ROADMAP.md:29-57`
