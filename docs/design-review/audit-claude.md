# 外部設計・内部設計・UI の監査（Claude）

- 調査日: 2026-10-29
- 調査者: Claude Code（Claude Opus 5.5）
- 対象: `index.html`（2,360行）、`js/data.js`、`js/compat.js`、`sw.js`、`manifest.json`、`tests/`、`docs/`（ROADMAP・DECISIONS・db/SCHEMA.md）、`supabase/migrations/` の一部

## 調査方法

- コードを全部読んだ。行番号は `index.html:行` の形で書く
- 見た目は、手元でアプリを開き（`python -m http.server`）、**架空のデータ**（`tests/fixtures/compat-fixture.json` に、今月の記録・シフト・予定を足したもの）を入れて、iPhone と同じ幅（390×844）で各タブと入力画面を撮って確かめた
- 本番のデータ・Supabase には触れていない。保存の操作もしていない
- Codex の監査（`audit-codex.md`）は見ずに書いた

## 結論

データの層（`js/data.js`）と DB は、テーブル分割のあとで良い形になった。弱いのは、その上に乗っている **画面と計算（`index.html`）** のほう。いちばん大きいのは次の5つ。

1. **「お金がいくらあるか」の数字の決め方が、場所ごとにばらばら**。ホームに「今日使える」「収支見通し」「残高推移」「予算」の4つの数字があり、それぞれ対象の期間と、入れるもの・入れないものが違う。同じ画面に「予算を超えています」と「収支見通し +18万円」が並ぶ。現金の支出は口座の残高に入らないのに、予定の予算（現金）は残高のグラフから引かれる
2. **日付の「今日」が、アプリを開いた瞬間のまま止まる**（`index.html:811-813`）。iPhone のホーム画面アプリは閉じずに裏に残るので、翌朝に開くと「今日」が昨日のまま。記録の日付の初期値・今日使える金額・ホームの今日の予定がずれる
3. **お金の計算が `index.html` の中で5か所に書き分けられていて、テストがない**。「ある日にどのお金が動くか」（給料・固定費・カードの引き落とし・予定）を、残高の推定・グラフ・見通し・カレンダー・ホームのお知らせが、それぞれ別に計算している。直すと別の場所とずれる
4. **新しい機能を載せる場所がない**。D9 で「新しい機能は互換の `st` に積まない」と決めたが、`st` を通らずに行を読み書きする仕組みはまだない。ROADMAP は「Phase 3 タスク → Phase 4 ファイル分割」の順なので、このままタスクを作ると D9 を破るか、その場しのぎの道ができる
5. **画面の構成が「お金管理アプリ」のまま**。タブは5つで、予定はカレンダー、シフトは別タブ、カード・固定費は設定タブ、バイト先はシフトタブにある。タスクを足す場所がなく、アプリ名も「お金管理」「バイト学生向け家計管理アプリ」のまま（`index.html:8-11`、`manifest.json`）

良いところも多い。送信待ち（outbox）・競合の扱い・1操作1トランザクション・履歴での復元は、通知や分析を足すときの土台としてそのまま使える。互換層をはっきり分けた判断（D9）も正しい。

## 外部設計の問題

### 高: お金の数字の決め方がばらばら

| 数字 | 計算 | 対象 |
|---|---|---|
| 推定残高 | 基準日の残高 ＋ 給料・固定収入・口座振込の収入 − 口座の固定費・カードの引き落とし・ATM（`index.html:1375`） | 基準日〜今日 |
| 今日使える | （残高 − まだの確定引き落とし − **これからの全部の予定の予算**）÷ 給料日までの日数（`index.html:1447`、`1427`） | 期限なし |
| 今月の収支見通し | 残高 ＋ 予定収入 − 確定引き落とし − 集計中カード − **今月の予定の予算**（`index.html:1445`、`1428`） | 「今月」と書いてあるが、給料日を過ぎると**来月入る給料**も足す（`index.html:1423`） |
| ホームの状態カード | 残高 − 確定引き落とし − 全部の予定の予算。マイナスなら「不足」、なければ予算と比べる（`index.html:2308-2326`） | |
| 残高推移グラフ | 日ごとに給料・固定費・引き落とし・**現金払いの予定の予算**を足し引き（`index.html:1380-1417`） | 90日 |

困ること:
- 架空データでは、同じ画面に「今月の予算を超えています」「今日使える ¥6,968」「収支見通し ＋¥183,699」が並んだ。どれを信じて行動すればよいか分からない
- **現金の支出は口座の残高に入らない**（ATM で引き出したときに引く考え方）。なのに、現金払いの予定の予算はグラフで予定日に口座から引かれる。予定の日が過ぎると、その分グラフが戻る
- 状態カードの「支出を記録すると、残高と見通しがすぐに更新されます」（`index.html:2315`）は、現金の支出では成り立たない
- カード払いの予定は、「集計中カード」（`cycle(card,1)` が予定の予算も足す、`index.html:1366`）と「予定支出」（`thisMonthPlanBudget`、`index.html:1428`）の両方に入るので、収支見通しで二重に引かれる（`index.html:1445`）

直す方向: 先に「現金・口座・カードのお金の動きをどう数えるか」と「ホームで一番大事な数字は何か」を決める（ユーザーが決める設計判断）。そのあと、数字の計算を1か所にまとめる（内部設計の高を参照）。

### 高: 同じ概念が2か所にある・置き場所がばらばら

- **毎月の収入が2つある**: 「固定費の登録」で種別を「収入（毎月入金）」にしたもの（`index.html:709`）と、「その他の固定収入」（`index.html:721-726`）。DB も `fixed_costs`（kind=income）と `fixed_incomes` の2テーブル
- **給料の締め日・給料日が2つある**: 設定タブの「バイト給料サイクル（新規バイト先の初期値）」と、バイト先ごとの値。説明には「新しいバイト先の初期値」とあるが、実際は**バイト先に値がないときの代わり**として、今のバイト先の計算にも使われる（`index.html:1298`）
- **バイト先の締め日は、給料の計算に使われていない**。給料は暦の月（1日〜末日）のシフトの合計で計算する（`index.html:1294`、`1319`）。締め日はカレンダーの表示とお知らせにだけ使う（`index.html:1299` を呼ぶのは表示の3か所だけ）。月末締め以外のバイト先だと、見込みの給料がずれる（今のデータで影響があるかは確かめていない）
- 置き場所: カードと固定費は設定タブ、バイト先はシフトタブ、ATM の引き出しはホームのボタンと設定タブの履歴、カードの引き落とし実績は設定タブの奥、給料の実績はシフトタブ

直す方向: 「登録しておくもの（カード・バイト先・固定のお金・カテゴリ）」と「日々の記録（支出・予定・シフト・タスク）」と「見るもの（ホーム・分析）」に分けて、画面の構成を考え直す。毎月の収入は1つにまとめる。

### 高: 削除に確認も取り消しもない

予定・シフト・家計簿・固定費・固定収入・ATM の「削除」は、押した瞬間に消える（`index.html:1744`、`1819`、`1939`、`2119`、`2156`、`2165`）。削除ボタンは「編集」の隣にある 48×29px の小さなボタン（撮影で計測）。DB には履歴（`private.row_history`）があるが、戻すには SQL が要る。

直す方向: 押したあと数秒「元に戻す」を出す（送信待ちに入る前なら、手元だけで戻せる）。

### 中: 編集できないものがある

シフト・固定費・固定収入・ATM の引き出しは、削除しかできない（`index.html:1836`、`2157`、`2164`、`1818`）。ATM の引き出しは日付が必ず今日になる（`index.html:1817`）。時間を変えたいシフトは、消して作り直すしかない。

### 中: ホームの「今後のイベント・予定」は今月の分だけ

今月の末日までしか出さない（`index.html:1447` の `mEnd`、`monthShifts(y,m)`）。月末になると、翌月の頭に旅行や給料日があっても「今後のイベントなし」になる（10/29 の架空データで確認）。

### 中: 保存のされ方が場所で違う・知らせ方が正しくない

- 設定タブの上のほう（残高・予算・扶養など）は、いちばん下の「設定を保存」を押さないと保存されない。ボタンは上から約3,950px（約4.7画面）下にある。同じタブのカード・固定費・カテゴリは「追加」を押した瞬間に保存される
- 「設定を保存しました！」を `alert` で出す（`index.html:2180`）。実際は送信待ちに入っただけで、通信できないときはまだサーバーに保存されていない

### 中: 削除したカード・バイト先が、表示に出続ける

カレンダーの「締め日」「引き落とし」「給料日」と、ホームのお知らせ・日の詳細は、削除済みのカード・バイト先も数える（`index.html:1519`、`1535`、`1649`、`1425`）。架空データでは、削除したカードが日の詳細に「¥0」で出た。

### 中: 扶養の壁が古い可能性がある

選べるのは「103万円」「130万円」だけで、DB の制約でも決め打ちしている（`index.html:703`、`supabase/migrations/20261029075718_table_split_tables.sql:134`）。2025年の税制改正で、所得税がかかり始める年収や、19〜22歳の子の扶養（特定扶養控除）の年収の条件が変わったはず。今の制度で何を見張るべきかを確かめる必要がある（ここは推測で、確かめていない）。

### 低: 入力の流れ

- 収支の記録で「名前・メモ」と「備考」の2つの入力欄がある（`index.html:794`）
- 支出の支払い方法は「現金」とカードだけ。口座から直接払う支出（デビット・振込）は記録できない（DB の制約も支出は cash か card）
- 家計簿の日ごとのまとまりは、はじめ全部閉じている。中身を見るのに毎回タップが要る

## 内部設計の問題

### 高: 「今日」が止まる

`_now`・`TODAY` はスクリプトを読み込んだときに1回だけ決める（`index.html:811-813`）。`gY()`・`gM()`・`gD()` もこれを使う（`index.html:1290`）。アプリに戻ってきたときは読み込み直すが（`index.html:1197-1206`）、日付は更新しない。一方で給与の表だけは `new Date()` を使っていて（`index.html:1851`）、同じ画面で「今日」が2つある。

直す方向: 「今日」を関数にして、戻ってきたとき・日付が変わったときに描き直す。小さい変更で、毎日使うので先に直したい。

### 高: お金の計算が5か所に分かれていて、テストがない

「ある日にどのお金が動くか」を、次の場所がそれぞれ書いている。

| 場所 | 行 |
|---|---|
| 推定残高 | `estimateAcct`（1375） |
| 残高推移グラフ | `buildBalanceSeries`（1380-1417） |
| これからの収入・引き落とし | `upcomingIncome`・`upcomingFixed`（1423-1424） |
| カレンダーの日の詳細 | `buildDay`（1631-1694） |
| ホームのお知らせ・今後の予定 | `renderHome` の後半（1447） |

カードの集計も、`cycle`（1347-1368）と `cardCycleForBillMonth`（1333-1346）に同じ合計の処理が2回書いてある。グラフの中には「二重に数えるバグがあった」というコメントもある（`index.html:1390-1393`）。上の「数字の決め方がばらばら」は、この重複から生まれている。

どれも `st` とグローバルの関数を直接読むので、node のテストから呼べない。テストがあるのはデータの層と互換層だけ（`tests/*.mjs`）。

直す方向: 「期間と設定を受け取って、お金の出来事（日付・金額・種類・どこのお金か）の一覧を返す」純粋な関数を1つ作り、残高・グラフ・見通し・カレンダーはそれを集計するだけにする。この関数は、あとで通知（サーバー側）や「予定と支出」の分析でも使い回せる。ROADMAP の Phase 2「計算ロジックを関数として切り出し、テストを書く」と同じ。

### 高: 新しい機能を載せる道がない（ROADMAP と D9 の食い違い）

- D9 は「新しい機能を互換の `st` に積み続けない。DB 側は ID が中心」と決めた
- ROADMAP は Phase 3（タスク）が Phase 4（ファイル分割）より先
- 今の画面は全部 `st` を読み書きする。`st` を通らずに行を読み、操作を送る入り口（たとえば「テーブルの行を取る」「変更を送信待ちに積む」）はない。`apply_op` も受け付けるテーブルを決め打ちしている（`supabase/migrations/20261029080421_table_split_apply_op.sql:86`）

このままタスクを作ると、`st.tasks` を足して互換層を広げる（D9 に反する）か、タスクだけ別のやり方で作ることになる。後者なら、それを「新しい作りの最初の1つ」として意図して作るほうがよい。

### 中: 配列の番号で記録を指している

編集・削除のボタンは `onclick="delLedger(12)"` のように配列の番号を埋め込む（`index.html:1676`、`1688`、`2087` など）。DB は ID になったが、画面はまだ番号。月表示の日の詳細（`#day-detail`）は、アプリに戻ってきて読み込み直しても描き直されない（`index.html:958-961` → `renderCal` は月表示のとき日の詳細に触れない）。別の端末で記録を消したあとに、古い詳細の「削除」を押すと、**別の記録を消しうる**。

直す方向: ボタンには `_id` を持たせる。読み込み直したら開いている詳細も描き直す。

### 中: 文字列で HTML を組み立て、エスケープしていない

予定の名前・メモ・カテゴリ名などを、そのまま `innerHTML` に入れる（例 `index.html:1677`、`1947` の `onclick="selCat('${c}')"`）。自分のデータだけなので危険は小さいが、名前に `'` や `<` が入ると表示やボタンが壊れる。タスクのように自由に文字を入れる機能が増えると、起きやすくなる。

### 中: 祝日の取得が、カレンダーの表示を止める

月表示は、前月・今月・翌月の祝日を Google Calendar API から**1か月ずつ順番に**取ってから描く（`index.html:1490-1493`、`1512`）。結果はメモリにしか置かないので、起動のたびに取り直す（`index.html:1454`）。手元で試したときは、取得に失敗するまで数秒、カレンダーが空だった（手元のアドレスからは API キーが通らなかったため。本番での速さは確かめていない）。通信できないときも同じように待つ。

直す方向: 先に描いて、祝日はあとから足す。祝日は端末に保存する（1年分が少ない）か、祝日の表をアプリに持つ。

### 中: 状態と描画のしくみ

- グローバルの変数が多い（画面の状態だけで `index.html:817-829` に30個以上）。入力シートごとに `ldgType`・`ldeType` のような「新規用」と「編集用」の変数が二重にある
- 変更のあとの描き直しは、関数ごとに手で並べている（例 `saveLedger` は5つの描画を呼ぶ、`index.html:1969`）。漏れると古い表示が残る
- `renderHome` と `openLedgerModal` を、ファイルの最後で上書きしている（`index.html:2328-2339`）。使っていない `saveLocal(){}`（`index.html:1102`）も残っている

### 低: 読み込み・配信

- supabase-js を `@2`（版の固定なし）で読む（`index.html:16`）。Service Worker は初めて取ったものをキャッシュするので、キャッシュ名を上げた日に、確かめていない新しい版が入りうる
- `sw.js` は先にキャッシュを見るので、デプロイのたびに `CACHE_NAME` を手で上げる必要がある（ROADMAP Phase 2 に項目あり）
- 日付の文字列を `new Date('2026-10-01')` で読む箇所がある（`index.html:1294-1295`）。これは UTC として読まれる。日本の時刻では結果が同じなので今は困らないが、ほかの箇所（`ds2d`）とやり方がそろっていない

## UI の問題

撮影は iPhone と同じ幅（390×844）で行った。

### 高: よく使うものが奥にある

- シフトタブ: いちばん上に「扶養」、次に「給与の実績入力」（バイト先ごとに1〜12月が並ぶ）。いちばん使う**シフト一覧は上から約2,900px**、バイト先の一覧は約4,100px の位置にある

- ホーム: 約2,200px。大事な数字（残高・今日使える・状態カード）は1画面目に入っているのは良い。ただ、2画面目以降に「見通し」「シフト収入・支出・集計中カード」「カードの予測」「予算」が続き、同じ金額が何度も出る

### 中: 押しにくい・読みにくい

- 編集・削除のボタンは 48×29px（Apple の目安は 44×44px）。編集と削除が隣り合っている
- カレンダーの月表示のラベルは 8.5px（`index.html:193`）で、金額が「-¥1,7…」のように切れる。下のタブの文字は 10px（`index.html:83`）
- 予定の入力シートは長く、「追加」ボタンが1画面に入らない（スクロールが要る）
- 入力シートは、外側をタップしても下にスワイプしても閉じない（上のつまみは飾り）。閉じるのは「キャンセル」だけ
- 右上のアカウントのボタン（`index.html:447-451`）と左上の送信待ちの表示（`index.html:496-502`）は画面に固定されていて、スクロールするとカードの角や見出しに重なる

### 中: 一貫性

- 家計簿の「収支」だけ、数字が上でラベルが下（`index.html:634`）。金額の書き方も「¥-76,270」と「-¥76,270」が混ざる（`index.html:2039`）
- 追加のボタンが重複している: カレンダーでは日の詳細の中に「＋予定・＋シフト・＋支出」、その下にも「＋シフトを追加・＋予定を追加」がある
- 色は CSS の変数があるのに、直接書いた色（`#185FA5`・`#A32D2D` など）が多い。インラインの `style=` も多い。ダークモードの見た目は確かめていない

### 中: アクセシビリティ（読み上げ・キーボード）

- 下のタブ・チップ（支払い方法・カテゴリ）・色の選択・カレンダーの日は、`<div onclick>` で作られていて、ボタンとして扱われない（`index.html:751-770` など）。`aria-` は3か所だけ
- 入力シートに `role="dialog"` がなく、開いても読み上げの焦点が移らない
- 支出は赤・収入は緑のように、色だけで意味を伝える箇所がある（多くは「-」「+」も付いているので、影響は小さい）

## 今後の機能（タスク・通知・予定と支出・月ごとの推移）に向けた弱点

| 機能 | 今の弱点 | 必要になるもの |
|---|---|---|
| タスク | 置く画面がない（5タブが埋まっている）。予定に「完了」のチェックがあり、タスクと役割がかぶる（`index.html:1677`、ROADMAP Phase 3 の最後の項目）。`st` を通らない道がない | 画面の構成の決定、D1〜D3、行を直接扱う入り口、`apply_op` に `tasks` を足すマイグレーション |
| 通知 | 「残高が足りない」などの判断は、端末の JavaScript の中にしかない。サーバーから通知を送るには、同じ計算をサーバーでも動かす必要がある | お金の計算を、DOM に触らない純粋な関数にする（Edge Function でも動く形）。D6 |
| 予定のときの支出 | 家計簿の記録と予定がつながっていない（`ledger_entries` に予定の ID がない）。予定の「予算」は見込みで、実際にいくら使ったかと比べられない | 記録に予定をひもづける列（任意）か、日付で推定するルールの決定 |
| 月ごとの支出の推移 | 家計簿のグラフ（年表示）に「月別支出推移」はすでにあるが、暦の1年分だけ。カードの支出を使った日で数えるか、引き落としの月で数えるかが決まっていない | 「支出」の定義（上の「数字の決め方」と同じ問題）。集計も純粋な関数に |

どの機能にも共通するのは、**「お金の出来事」を1か所で作る関数** と、**`st` を通らずに行を扱う入り口** の2つ。

## 進め方の提案

「先に内部設計と UI を直してからタスク」か「タスクが先」かについて。

**全部を直してからタスク、はおすすめしない。** Phase 4（Vite・TypeScript・全部のファイル分割）を先にやると、数週間、使える機能が何も増えない。毎日使っているアプリを大きく書き換える危険もある。

**今の作りにそのままタスクを足す、もおすすめしない。** D9 を破るか、`st` の外に場当たりの道ができる。5タブにさらに1つ足すと、あとで画面の構成を変えるときに作り直しになる。

**おすすめは、タスクの前に「最小限の土台」だけ作る順番。**

1. **すぐ直す小さなバグ（それぞれ小さな PR）**
   - 「今日」が止まる（`index.html:811-813`）
   - 削除の「元に戻す」
   - ホームの「今後の予定」を今月で切らない
   - 状態カードの説明文・「設定を保存しました」の知らせ方
   - 削除したカード・バイト先を、締め日などの表示から外す
2. **決めること（ユーザーが決める。DECISIONS に足す）**
   - 画面の構成: タスクをどこに置くか。たとえば「シフトをカレンダーにまとめて、空いたタブをタスクにする」「カレンダーを『予定・タスク』にする」「設定を『登録』と『設定』に分ける」など
   - お金の数え方: 現金の支出・口座の支出・カードの支出を、残高と予算にどう入れるか。ホームでいちばん大事な数字はどれか
   - D1〜D3（タスクの保存先・予定との関係・最初の項目）。D1 はテーブル分割が済んだので、実質「新しいテーブル」になる
3. **土台（1〜2 PR）**
   - `st` を通らずに、テーブルの行を読み、変更を送信待ちに積む小さな入り口を `js/data.js` の上に作る
   - タスクは、その入り口を使う最初の機能として、別ファイルで作る（D4 のファイル分割の最初の一歩にもなる）
4. **タスク（最小版）**
5. **お金の計算を1か所にまとめてテストする**（Phase 2 の項目）。数え方を決めたあとにやる。予定と支出・通知・月ごとの推移は、そのあとに載せる
6. 残りの UI の整理と、ほかのタブを1つずつ新しい作りに移す（Phase 4）

この順番だと、ROADMAP の Phase 3 と Phase 4 の一部が入れ替わる。直すかどうかは、ユーザーが決める。
