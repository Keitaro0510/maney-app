## D1: タスクをどこに、どの道で保存するか

2026-10-31 に書き直した。最初の版の選択肢は「JSONB 1行の `st` に足す」と「`tasks` テーブルを作る」だったが、2026-10-29 にテーブルに分けて JSONB の1行（`user_data`）への書き込みを止めたので、前者はもうない。最初の版で心配していた RLS とオフラインの扱いは、今のテーブルの作り（本人の行だけ・送信待ち・競合の検出）で解決している。残る問いは「どのテーブルに」と「画面からどの道で保存するか」。

- **(a) 新しい `tasks` テーブル。互換の `st` を通さず、データの層（`js/data.js`）で直接読み書きする**: D9・D12 と合う。送信待ち・競合の検出・1操作1トランザクション・履歴での復元は、今の仕組みをそのまま使える。`st` の外を保存する入り口（D12 の手順5）が要る
- **(b) 新しい `tasks` テーブル。互換の `st` に `tasks` を足し、互換層で変換する**: 今の画面と同じ作りなので早い。D9（新しい機能を `st` に積まない）を破り、Phase 4 で互換層を消すときに作り直しになる
- **(c) `plans` テーブルに「タスク」の種類を足す**: 予定と同じ画面・カレンダーにそのまま出せる。ただし `plans` は日付が必須（`start_date not null`）で、期限のないタスクと合わない。`plans` は互換層を通るので、(b) と同じく D9 を破る。予定の `done` はお金の計算に使っているので（下の D2）、意味が混ざる

決定: (a) 新しい `tasks` テーブルを作り、互換の `st` を通さず、データの層（`js/data.js`）で直接読み書きする（2026-10-31）

理由:
- D9・D12 と合う。画面用の互換の `st` には載せない、という境界を守れる
- 送信待ち・競合の検出・1操作1トランザクション・履歴での復元に、そのまま乗せられる

作るときの注意: `tasks` を `TABLES` に足すだけでは足りない。今の画面の `save()` は、互換の `st` から作った行（`tasks` を含まない）と、サーバーの写しを全テーブルで比べる（`diffRows`）ので、タスクを全部「消えた」と見なしてしまう。互換層が扱うテーブルと、直接扱うテーブル（`tasks`）を分けてから足す。たとえば、比べる前に `tasks` の行はサーバーの写しのものをそのまま入れる（D12 の手順5）

DB の側では、テーブルの名前を固定で並べている所が3つある。マイグレーションで `tasks` をどれにも足す（足さないと、タスクだけ履歴・写し・復元から漏れる）:
- 時刻・履歴のトリガー、RLS、権限（`supabase/migrations/20261029075718_table_split_tables.sql` の最後）
- `apply_op` で保存できるテーブル（`20261029080421_table_split_apply_op.sql`）
- 毎日の写しと、写しからの復元（`private.snapshot_tables()`、`20261029083204_table_split_restore.sql`）

アプリの側の `js/data.js` の `TABLES` と合わせた4か所を、同じ PR で変える。（2026-10-31 追記: JSON の読み込み（D13）が読むテーブル `private.import_tables()` は、写しのテーブルから作るので、足す所は増えない。DB のテスト `08_import_backup` と Node のテスト `tests/backup.test.mjs` が、どちらも同じ並びになっているかを確かめる）「`tasks` が写しに入り、写しからの復元でも戻る」ことを確かめる DB のテストを、少なくとも1つ付ける。

## D2: タスクと予定の関係

今の予定には「完了」のチェック（`plans.done`）がある。これは「やり終えた」ではなく、お金の計算に効いている。完了にした予定は、予算を見込みの支出から外し、ホームのお知らせ・今後の予定からも消える（`index.html:1344`・`1366`・`1407`・`1427-1428`・`1447`）。

- **(a) 予定とは別のもの（予定とつながらないタスク。期限はあってもなくてもよい）**: いちばん単純。「予定 = その日にあること」「タスク = やること」とはっきり分かれる。予定の準備（「旅行の前に宿を予約する」）は予定とつながらないが、あとで `tasks` に `plan_id` を足せばつなげられる（ROADMAP の Phase 6「予定にひもづく準備のタスク」）
- **(b) 予定の中のチェックリスト**: 予定の準備には便利。予定のない「やること」（レポートを出す、など）を置けないので、タスク管理にはならない
- **(c) 両方（別のタスクで、予定にもひもづけられる）**: いちばん柔軟。最初の版が大きくなる。Phase 6 の項目を前に持ってくることになる

合わせて決めること: 予定の「完了」のチェックをどうするか

- そのまま残す。意味が「済んだ（予算を見込みに入れない）」なので、言葉を「済み」などに変えてタスクの「完了」と分ける
- そのまま残す（言葉も変えない）
- なくす。予定の予算は、日付が過ぎたら見込みから外す（お金の数え方が変わるので D11 にかかわる）

決定（2026-10-31）:
- (a) タスクは予定とは別のもの。期限はあってもなくてもよい。予定とのひもづけは、Phase 6 で `tasks` に `plan_id` を足して作る
- 予定の「完了」のチェックは残す。画面の言葉は「済み（予算に含めない）」のように変える。DB の列名 `done` は今は変えず、D11 でお金の意味を考え直すときに見直す

理由:
- 「予定 = その日にあること」「タスク = やること」と分けるのがいちばん単純で、最初の版を小さくできる
- 予定の「完了」は、ただ「やり終えた」ではなく「今後の見込み・お知らせから外す」という働きをしている。それを使う人に伝える言葉にする
- 列名を変えると、互換層・移行・テストに広く手が入る。お金の意味を考え直す D11 と一緒にやるほうが安全

## D3: 最初のタスクに持たせる項目

- 候補: タイトル、期限、完了、優先度、くり返し、メモ、ひもづく予定
- 最初の版ではどこまでにするか

2026-10-31 に、ここまでの決定で決まったものを分けた。

もう決まっているもの:
- **タイトル**（必須）
- **期限**（あってもなくてもよい。D2）
- **完了**（D10 で、完了できる場所はタスクのタブと開いたときの一覧に決めた）
- **くり返し**・**ひもづく予定**（`plan_id`）は最初の版に入れない（ROADMAP の Phase 6。D2）

決めること:
1. **期限は日付だけか、時刻も持つか**
   - 日付だけ: 簡単。開いたときの一覧（今日・2週間以内）とカレンダーは日付で動くので足りる
   - 日付と、あってもなくてもよい時刻: 「17時までに提出」が書ける。期限切れを時刻で判定するか、並べ方、表示が少し増える
   - 時刻の列はあとから足しても、今のタスクは壊れない（空でよい列を足すだけ）
2. **完了の持ち方**
   - 完了した・していない（`true` / `false`）
   - 完了した日時（`completed_at`。まだなら空）: 「いつ終えたか」がわかる。完了したものを最近の順に並べる、何日かたったら一覧から隠す、などがあとでできる。手間はほぼ同じ
3. **メモ**
   - 入れる: 文字の列を1つ足すだけ。入力画面が1行増える。予定にもメモがあるのでそろう
   - 入れない
4. **優先度**
   - 入れない: 期限の順に並べれば足りる。最初の版を小さくできる
   - 「大事」の印だけ（ある・ない）
   - 3段階（高・中・低）
5. **並べ方**
   - 期限の早い順（期限のないものは下）に自動で並べる。手で並べ替えはしない
   - 手で並べ替えられる（ドラッグの UI が要る）
6. **削除**
   - 本当に消す: タスクはほかの記録から指されていないので、消しても困らない。消したあと数秒「元に戻す」を出す。90日以内なら履歴（`private.row_history`）からも戻せる
   - 消さずに `deleted_at` を入れる（カード・バイト先・カテゴリと同じ）: 戻すのが簡単。消したタスクが DB に残り続け、読み込みとエクスポートで外す必要がある

決定（2026-10-31）:
- 最初の版の項目: タイトル（必須）、期限（日付だけ。なくてもよい）、完了した日時（`completed_at`。まだなら空）、メモ
- 入れないもの: 期限の時刻（あとで足せる）、優先度、くり返し・ひもづく予定（Phase 6）
- 並べ方: 期限の早い順に自動で並べる（期限のないものは下）。手で並べ替えはしない
- 完了したタスク: 消さずに、横線で薄くして、その場に残す（予定のチェックと同じ見た目）。完了して7日たったら（`completed_at` から数える）、タスクのタブのいちばん下の「完了したタスク」にたたむ（開けば見られる）。完了を取り消すと、`completed_at` は空に戻す
- 削除: 本当に消す。消したあと数秒「元に戻す」を出す。完了とは別の操作で、いらなくなったタスク（まちがえて作った・やめた）に使う

理由:
- 開いたときの一覧とカレンダーは日付で動くので、日付だけで足りる。時刻の列は、あとから足しても今のタスクは壊れない
- 完了した日時を持てば「いつ終えたか」がわかり、7日でたたむのもこれで決められる
- 「あれ、やったっけ？」と確かめたくなることが多いので、完了したタスクは見えるように残す
- 削除は「いらなくなった」ときの操作なので、完了と分け、本当に消すほうが一覧がすっきりする。タスクはほかの記録から指されていないので、消しても困らない
- 最初の版を小さくするため、優先度と手での並べ替えは入れない

## D4: ファイルを分割するやり方

- **ビルドなし**（ブラウザの ESモジュールで分割）→ あとで Vite に移る
- **最初から Vite と TypeScript**

2026-11-01 に、今のコードの形を見て選択肢を出し直した（`index.html` は 2,846行で、CSS 691行・JavaScript 1,712行・関数 約230個。HTML の中に `onclick="関数名()"` が100か所あり、画面を作る文字列の中にもある。`js/` の11ファイルはふつうの `<script>` で動いている）:
- **(a) 今の形（ふつうの `<script>`）のまま機能ごとに分け、型は JSDoc＋TypeScript の検査だけ**: ビルドが要らず、本番への危険がいちばん小さい。関数どうしのつながりは見えにくいまま
- **(b) ビルドなしで import/export（ES モジュール）にする**: つながりがはっきりする。`onclick` を全部書き換える必要がある
- **(c) 最初から Vite と TypeScript**: 型の恩恵を最初から受けられる。変更がいちばん大きい

決定: (c) 最初から Vite と TypeScript。ただし一度に書き直さず、土台から段階的に移す（2026-11-01）

進め方:
1. 公開を GitHub Actions に移す（D15 で済んだ）
2. Vite を入れ、まず今の JavaScript は `.js` のまま動かす
3. TypeScript の検査（`checkJs`）を入れて、型の間違いを直す
4. 機能ごとに `.ts` と import/export に移す
5. `onclick` を、少しずつイベントの登録（`addEventListener`）に置き換える。移す間は、モジュールの関数を `window` に出す互換の層を置く
6. ビルドしたファイルを元に、Service Worker の先読みの一覧（precache）と版を作って公開する（Vite だけでは `sw.js` の一覧は作られない）

最初に、Windows のアプリケーション制御が Vite の使う esbuild（`.exe`）を止めないかを、小さなビルドで確かめる（`supabase.exe` は止められている）。

理由:
- 長く使うアプリなので、最終形は Vite＋TypeScript のきれいな形にしたい
- 一度に全部を `.ts` に書き直すと、毎日使っている画面を壊しやすい。段階に分ければ、1つずつ PR にして確かめられる
- Vite は `onclick` を自動では救わないので、互換の層を置いて少しずつ置き換える

## D9: 試験版（next.html）で、新しいテーブルのデータを画面にどう渡すか（テーブル分割 #11）

- **データの層だけ差し替える**: テーブルから今と同じ形の `st` を組み立て、各記録に ID を持たせる。画面と計算のコードはほぼそのまま。変えるのは読み込み・保存と、編集の処理（ID で操作を作る）だけ
- **画面と計算も新しい形にする**: `st` をテーブルの形（ID で参照）にして、画面と計算のコードも書き換える。ほぼ全体の書き換えになり、古い版と計算を比べるテストが必須になる

決定: データの層だけ差し替える（2026-10-29）。ただし、これは移行のためだけの「互換層」として、はっきり切り分ける

```
DB のテーブル（正規化・ID が中心）
  ↓ 変換
互換の st（今の画面と計算のためだけ）
  ↓
今の画面・計算
```

理由: 毎日使っているアプリなので、まず安全に移行したい。互換の `st` は仮の設計と割り切る。新しい機能を互換の `st` に積み続けず、DB の側は最終形に近い ID が中心の設計で始める。Phase 4 などで画面と計算を作り直すときに、`st` を経由せず DB のモデル（ドメインモデル）を直接読む形に置き換える。そうすれば今回は安全に移行でき、あとの全面的な作り直しも無駄にならない

## D10: 画面の構成（タスクをどこに置くか）

設計の監査（[design-review/README.md](design-review/README.md)）で、今の画面の構成が「お金管理アプリ」のままで、タスクを置く場所がないことがわかった。今の構成は [SCREENS.md](SCREENS.md)。

D2 で、タスクは予定とは別のもので、期限のないものもある、と決めた（2026-10-31）。なので、どの案でも「タスクの一覧」を置く場所が要る。ROADMAP の Phase 3 では、ほかにホームに「今日・期限切れのタスク」、カレンダーに期限を出す。

前提: タブはこれ以上増やさない（5つのまま。2026-10-31 にユーザーが決めた）。なので、最初にあった「6つ目のタブを足す」案は外した。

- **(b) シフトタブをなくし、空いたタブをタスクにする**: シフトの一覧と追加はカレンダーへ（もう出ていて、追加もできる）。給与の実績の入力と今年の収入（扶養）は家計簿へ、バイト先は設定へ移す。予定とシフトはカレンダー、お金は家計簿、登録しておくものは設定、と分かれ、監査の「登録・日々の記録・見るもの」の分け方に近づく。ただし、タスクの前に4つの区画を動かす（D12 では「今ある画面はあとで1つずつ直す」）。毎月使う給与の実績の入力を、家計簿の中で見つけやすくする必要がある。手間は大きい
- **(c) カレンダーのタブを「予定・タスク」にする**: カレンダーの上に「カレンダー / タスク」の切り替えを足す。今ある画面は動かさない。期限のあるタスクを、同じタブのカレンダーにも出せる。ただし、タスクの一覧はタブを押したあと、もう1回切り替える必要がある。カレンダーの上のほうが、今の「日・週・月」と合わせて混む。手間は中くらい
- **(d) 設定を右上のアカウントのメニューから開くようにし、空いたタブをタスクにする**: 設定の中身はそのままで、開く場所だけ変える。タスクは1回押せば開ける。ただし、設定の中の、ときどき使うもの（残高の基準の入力・カードの引き落とし実績・ATM の履歴）も1段奥になる。右上のボタンは小さく「？」の丸なので、そこに設定があるとわかりにくい。手間は小さい
- **(e) ホームにタスクを置く**: ホームのいちばん上に「今日・期限切れのタスク」を出し、全部の一覧は、そこから開く画面（タブではない）にする。今ある画面は動かさない。アプリを開いてすぐ見える。ただし、ホームはもう長く、お金の数字が下に押される。ホームの並びは D11（ホームでいちばん大事な数字）ともかかわる。全部の一覧は1段奥になる。手間は中くらい

今は手間の小さい案で始め、Phase 4 で画面を作り直すときに (b) のように整理し直す、という組み合わせもできる。

タスクを出す場所と役割:
- **タスクのタブ**: 全部のタスクを管理する（期限のないタスクも）
- **開いたときの画面**: ~~その日はじめて開いたときだけ出す（端末ごとに覚える）。右上の×で閉じるだけで、「今日は表示しない」のチェックは置かない~~ → 2026-10-31 に書き直した（下の「開いたときの画面の書き直し」）。並びは、期限切れ → 今日 → 2週間以内。期限のないタスクは出さず、0件なら出さない
- **ホーム**: 「今日・期限切れ N件」の1行だけ。押すと、開いたときの画面と同じ一覧を開く
- **カレンダー**: 月・週・日のどの表示でも、タスクは印と件数だけ。日の詳細には名前を出すが、見るだけ
- **完了できる場所**: タスクのタブと、開いたときの画面の2か所だけ（タスクを一覧で見ている場所）

カレンダーのセル: 整理する方向にする。支出・収入の金額の札をセルから外す（日の詳細と家計簿では見られる）。タスクとは別の小さな PR で、タスクの件数を足す前にやる。

あとで決めること（Phase 4 の候補）:
- (b)（シフトタブをなくす）
- 設定の中の分け方（お金の基本・登録するもの・実績の入力・アカウント）
- 「登録しておくもの」を1か所にまとめるか。固定費・カードなどの登録は、それまで設定に残す
- アプリの名前

理由:
- タスクは毎日開く見込みが高いので、独立したタブにして、1回押せば一覧に行けるほうがよい
- 期限はカレンダー、今日・期限切れはホームと開いたときの画面、全部の管理はタスクのタブ、と役割がきれいに分かれる
- (b) は、画面を整理するために、よく開くシフトの導線を悪くしてしまう
- 設定は、小さな丸にそのまま載せると見つけにくい。押しやすい大きさと、わかる名前が要る
- ログアウトはふだん使わず、押すと作業が途切れる。設定の上のほうには、よく触るもの（残高・基準日・予算）を置きたい
- 完了できる場所を「タスクを一覧で見ている場所」に限ると、迷わない。カレンダーは日付を見渡すための画面、と役割を固定できる
- 開いたときの画面は、何度も出るとすぐ邪魔になる。1日1回なら「今日は表示しない」は要らない。見逃したら、ホームから同じ一覧を開ける。「日付が変わったか」を見分ける仕組みは、バグ修正の「今日が止まる」と同じものを使える
- カレンダーに予定・固定費・締め日・タスクが並ぶので、金額まで出すと読む負担が大きい
- 固定費は、毎回の記録ではなく「毎月こう動く」という決まりなので、カード・カテゴリと同じく設定に合う。監査で見つけた固定費の問題（あとから編集できない）は、置き場所とは別に直す

### 開いたときの画面の書き直し（2026-10-31、ユーザーが決めた）

ユーザーから「ゲームのログインのお知らせのように、2週間以内の期限のタスクを出し、『今日は表示しない』のチェックを付けてほしい」と頼まれた（#71）。

- **(a) 開くたびに出し、「今日は表示しない」で止める**: 起動したとき・日付が変わったときに出す。ほかのアプリから戻ってきたときは、前に出してから1時間以上たっていたら出す（すぐ戻るたびに出ると邪魔なため）

- **(c) 今のまま（1日1回、チェックなし）**

決定: (a)（2026-10-31）

作り（#71 の10）:

理由:

- 邪魔なときは、その日だけ止められる

## D11: お金の数え方とホームの構成

監査で、ホームの「今日使える」「今月の収支見通し」「残高推移」「状態カード」の計算が、それぞれ違う期間と項目で数えていることがわかった（[audit-claude.md](design-review/audit-claude.md) の「外部設計の問題」）。お金の計算を1か所にまとめる前に、数え方を決める。

- **現金の支出**: 今は口座の残高に入れず、ATM で引き出したときに引いている。このままにして画面に説明を出すか、財布の残高を別に持つか
- **口座から直接払う支出**（デビット・振込）: 今は記録できない（支払い方法は現金かカードだけ）。記録できるようにするか
- **予定の予算**: 見込みの支出として、どの数字に入れるか（今は数字ごとにばらばら）。予定の「済み」（列名 `done`）の意味と名前も、ここで見直す（D2）
- **ホームでいちばん大事な数字**: 「今日使える金額」「月末の見込み残高」「今月の予算の残り」のどれか

決定（2026-10-31）:
1. **現金の支出**: 今のまま、口座の残高からは引かない（ATM で引き出したときに引く。財布は口座の外という考え方）。画面に「現金の支出は、引き出したときに引いています」と書く。財布の残高は持たない
2. **口座から直接払う支出**（デビット・振込）: 記録できるようにする。支出の払い方に「口座」を足し、その日に口座の残高から引く。今は使っていないが、銀行振込や、家賃を口座振込にすることがありうるため（2026-10-31 に変えた。最初は「今のまま」）。毎月くり返す支出の扱いは D14
3. **予定の予算**: 予定の日に、払い方どおりに1回だけ数える。カード払いの予定は、そのカードの引き落としに入れる。それ以外は、予定の日に出ていくお金として数える。「済み」にした予定は数えない（二重に引かない）
4. **ホームでいちばん大事な数字**: 「給料日までに使えるお金」。次の給料日の前の日に口座に残る見込みから、それまでの引き落とし・予定を引いた合計。下に小さく「1日あたり ¥〇・給料まで〇日」と、口座の残高（推定）を添える。0 で止めず、足りないときはマイナスのまま出す（赤）

ホームの構成（たたき台。使ってみて変える）:
1. いちばん大事な数字（1枚）
2. タスクの1行
3. 支出を記録・予定を追加（ATM で引き出すも、ここに小さく並べる）
4. 今日のお知らせ（引き落とし日・給料日など）
5. これからのお金の動き（2週間ぶんの給料・引き落とし・予定）。今の「今後のイベント・予定」と「カード引き落とし予測」を1つにまとめる
6. くわしく（ふだんはたたむ）: 残高推移のグラフ・今月の収支・予算の進み

「状態カード」と「今月シフト収入・今月支出・集計中カード」の3つの数字は、ホームから外す（家計簿・シフトのタブで見られるようにする）。

理由:
- ホームがごちゃついていて使いにくい（今は13個の部品と、数え方の違う6種類のお金の数字がある）。数字を1つの考え方にそろえれば、ホームに出すものを減らせる
- 現金を口座の外と考えるのは今のままで、数字を増やさずにすむ
- 口座から直接払う支出は今は使っていないが、振込や家賃の口座振込はありうるので、先に記録できるようにしておく
- 足りなくなるときは、0 ではなくマイナスで見えるほうが、どれだけ足りないかがわかる
- 予定の予算を1回だけ数えれば、カード払いの予定が二重に引かれる問題がなくなる
- 「給料日までに使えるお金」なら、1日あたりの額も同じ考え方で添えられ、「今日使える」と「見込み」を1つにまとめられる

## D12: タスクの前にどこまで直すか

- **(a) 何も直さずにタスクを作る**: いちばん早い。D9 を破って互換の `st` にタスクを足すか、保存のたびにタスクが消える危険のある道になる（[design-review/README.md](design-review/README.md)）
- **(b) 最小限の土台だけ直してからタスク**: はっきりしたバグ・`st` の外を保存する入り口・タスク用の UI 部品だけを先にやる。ROADMAP の Phase 2・4 の一部をタスクの前に移す
- **(c) Phase 4（Vite・TypeScript・全部のファイルの分割）を終えてからタスク**: いちばんきれい。長いあいだ使える機能が増えない。毎日使うアプリを大きく書き換える危険がある

Claude と Codex の監査は、どちらも (b) をすすめている。

決定: (b) 最小限の土台だけ直してからタスク（2026-10-31）。次の順番で進める（同じ日に、CI をバグ修正の前に、タグをバグ修正のあとに入れ替えた）

1. D10 と、書き直した D1〜D3 を決める。エクスポートするデータの形（`tasks` を含む）も、このときに決める
2. PR ごとにテストを動かす GitHub Actions を入れる
3. はっきりしたバグ4つを、1つずつ小さな PR とテストで直す（「今日」が止まる・月にない日・日をまたぐシフト・古いボタンから別の記録を消しうる）
4. 直した状態を確かめて、`v1.0.0` のタグを付ける
5. `st` の外のテーブルを読み書きする入り口と、`apply_op` に `tasks` を足すマイグレーション
6. タスク用の UI 部品（`<button>`・ダイアログ・44px のタップ領域）
7. タスクの機能（ROADMAP の Phase 3）
8. D11 を決めて、お金の計算を1か所にまとめる。JSON のエクスポート・インポート

Phase 4（Vite・TypeScript・全部のファイルの分割）は、タスクのあとにする。

`CACHE_NAME` の自動化は CI とは分ける。手で番号を上げる形ではなく、デプロイの版やハッシュと確実に連動させる形にする。そのやり方を決めてから入れる（今の Pages は main をそのまま公開していてビルドがないので、公開を GitHub Actions に移すかどうかも一緒に決める）。

理由:
- (a) は避ける。`tasks` の保存の道を先に整えないと、「機能はあるのに、次の保存で消える」という最悪の壊れ方になりうる
- お金の計算をまとめるのはタスクのあと。タスクとお金の計算はまだつながらない（つながるのは Phase 6）ので、D11 を先送りして、タスクを早く使えるようにする
- CI を先に入れると、バグ修正の PR に最初から自動のテストを通せる
- `v1.0.0` のタグは、「わかっている不具合を直し、CI で確かめられる最初の安定版」に付けるほうが、意味がはっきりする
- JSON の入出力はタスクのあとでよい。ただし、`tasks` を含むデータの形は D10 と一緒に先に決めておく

## D13: エクスポートするデータの形

JSON のエクスポート・インポートは、タスクのあと（D12 の手順8）に作る。ただし、`tasks` を含むデータの形は先に決めておく（D12）。

参考: DB の毎日の写し（`private.snapshots`）は、`{ "テーブル名": [行, 行, …], … }` の形で、全部の列を持っている（`supabase/migrations/20261029083204_table_split_restore.sql`）。

- **(a) テーブルの行のまま（毎日の写しとほぼ同じ形）**: DB と同じ形なので、そのまま戻せる。記録どうしのつながり（カードの ID など）が保たれる。毎日の写しから戻す処理と、考え方を共有できる。互換の `st` を Phase 4 で消しても、形は変わらない。人が読むには向かない（カテゴリなどが ID で書かれる）
- **(b) 互換の `st` の形に `tasks` を足す**: 切り替える前の JSON（`user_data`）に近い。ただし `st` は仮の形（D9）で、Phase 4 で消すので、形が変わってしまう。`tasks` は `st` に入れないと決めた（D1）
- **(c) 人が読める表（CSV。表計算のアプリで開ける）**: 家計簿を表計算で見られる。テーブルごとに別のファイルになり、つながりが ID なので、戻すのには向かない。見るための出力として、あとで別に足すことはできる

(a) にする場合に、合わせて決めること:
- 入れる列: `id` は入れる（つながりのため）。`user_id` は入れない（別のアカウントや、手元の Supabase にも入れられるように）。`created_at`・`updated_at` を入れるか
- 削除済み（`deleted_at`）のカード・バイト先・カテゴリも入れる（昔の記録が指しているため）
- ファイルに形の版の番号を入れる（形を変えたとき、たとえば期限の時刻を足したときに、古いファイルも読み込めるように）
- 仕組みのためのテーブル（`sync_state`・`applied_ops`・履歴・写し）は入れない
- インポートのやり方（全部を置き換えるか、足すか）は、作るときに決める

決定: (a) テーブルの行のまま（2026-10-31）

ファイルの形:

```json
{
  "format": "maney-export",
  "version": 1,
  "exported_at": "2026-10-31T12:00:00.000Z",
  "tables": {
    "settings": [],
    "cards": [],
    "tasks": []
  }
}
```

- `tables` の中は、DB の行に近い形。テーブルの名前は DB と同じ
- 入れる列: `id`、`position`、ほかのテーブルを指す ID（`card_id` など）、`deleted_at`、`completed_at` など、中身の列すべて
- 入れない列: `user_id`・`created_at`・`updated_at`（サーバーが決める列）。インポートするときは、ログインしている人の ID とサーバーの時刻を使う
- 削除済みのカード・バイト先・カテゴリも入れる
- 仕組みのためのテーブル（`sync_state`・`applied_ops`・履歴・写し）は入れない
- 形を変えたら `version` を上げ、古い版のファイルも読み込めるようにする

インポートのやり方（全部を置き換えるか、足すか）は、作るときに決める（→ 下の「インポートのやり方」で、全部を置き換えると決めた）。どちらでも次を守る:
- 中身を確かめてから書き込む
- 全部を置き換えるなら、その前に写しを取る
- 途中で失敗しても、半端な状態を残さない（1つのトランザクションで書く）

理由:
- エクスポートのいちばんの目的は、何かあったときに戻せること。DB と同じ形がいちばん確か
- 互換の `st` を Phase 4 で消しても、形が変わらない
- `created_at`・`updated_at` は、アプリのふつうの保存（`apply_op`）ではサーバーが付け直すので、入れても戻らない。入れると「戻るのか」があいまいになる（写しから戻すときだけは `maney.keep_created_at` で作った日時を残しているが、エクスポートでは使わない）
- 外側の形と版の番号を決めておくと、作るときに迷わない
- 表計算で見たくなったら、CSV は「見るための出力」として、あとで足せる

### インポートのやり方（2026-10-31、作るときに決めた）

- **(a) 全部を置き換える**: ファイルの中身が、そのまま今のデータになる。直前に写しを取るので、まちがえても戻せる。作りが単純で確か。古いファイルを読むと、そのあとの記録は消える（写しからは戻せる）。ほかの端末の送れていない変更は止まる
- **(b) 足す（ないものだけ）**: 今のデータは消さない。ファイルにあって今ない行だけを足す。消してしまった記録を取り戻すのに向く。変えてしまった記録は戻らない。カード名の重なりなど、制約に当たったときの扱いを決める必要がある
- **(c) 両方作って選べるようにする**: どちらにも使えるが、作る量とテストがおよそ倍

決定: (a) 全部を置き換える（2026-10-31）

作り（手順8の段5）:
- 書き出しはアプリだけで作る。今の行（サーバーの写しに送信待ちを重ねたもの。画面に出ている内容）をファイルにする（`js/backup.js`）
- 読み込みは DB の関数 `public.import_backup` が、1つのトランザクションで行う。`apply_op` は1回に500件までで、家計簿だけで1,000件を超えるため、別の関数にした
  - 中身を確かめてから書く。テーブルが1つでも欠けていたら止める（欠けたテーブルを空にしてしまわないように）
  - 書く前に、今の状態を写し（`before_import`、90日）に残す。`private.restore_snapshot` で戻せる
  - ログインしている人の行だけを消して入れ直す。カード・バイト先・カテゴリへの参照は (user_id, id) なので、他人の行は指せない。ほかの人の行と同じ id があれば止める（上書きしない）
  - 移行の番号（epoch）を上げる。ほかの端末の送れていない変更は、保存する前に止まる（「サーバーのデータが移し直された」の知らせ）。読み込む端末は、送れていない変更を先に送り、残っていたら読み込まない
- 読み込むテーブルは `private.import_tables()`（写しのテーブルから、もう使わない `fixed_incomes` を除いたもの。2026-11-01 に表を消してからは、写しのテーブルと同じ）。アプリの `MoneyData.TABLES` と同じにする

理由:
- エクスポートのいちばんの目的は、何かあったときに書き出したときの状態に戻すこと。置き換えなら、ファイルどおりの状態に必ずなる
- 足すやり方では、変えてしまった記録が戻らず、「戻したつもりで戻っていない」が起こりうる
- 直前の写しがあるので、置き換えでまちがえても戻せる

## D14: 毎月くり返す支出・収入（今の固定費）の入れ方と、やめ方

2026-10-31 にユーザーから。「毎月この日に、のように、くり返しの支出を記録の画面から入れられれば、設定画面で固定費を入れなくてよくなるのでは。かからなくなったときの扱いも含めて考える」。

今の作り:
- 固定費（`fixed_costs`）は「毎月この日にこの額」という**ルール**で、記録（家計簿の行）は作らない。推定残高・残高推移・カードの集計は、このルールから毎月の分を数える
- 毎月の収入は2か所にある（固定費の「収入」と、固定収入 `fixed_incomes`。監査の指摘）
- 入れるのも消すのも設定の画面。編集はできない（消して入れ直す）
- **消すと、過去の月の分まで計算から消える**。推定残高は「基準日から今日まで、毎月の固定費を引く」ので、解約したサブスクを消すと、もう払った月の分も引かれなくなり、残高が実際より多く出る

選択肢:
- **(a) ルールのまま、期間（いつから・いつまで）を持たせ、記録の画面から作る**
  - 「収支を記録」に「毎月くり返す」を足す。その日を毎月の日にして、その月からのルールを作る
  - かからなくなったら「やめる」で、いつまで（今月まで・先月まで）を選ぶ。過去の月は数え続ける。まちがえて作ったときだけ「削除」（過去からも消える。「元に戻す」付き）
  - 金額が変わったら「来月から金額を変える」。今のルールを今月までで終わらせ、来月からのルールを作る（過去の金額は変わらない）
  - 一覧は家計簿のタブの「毎月のお金」に置き、設定から外す。毎月の収入（固定収入）も同じものにまとめる
  - DB は `fixed_costs` に「いつから」「いつまで」の列を足し、`fixed_incomes` を移して1つにする（マイグレーションとテスト）。お金の計算は今の考え方のまま、期間の外の月を数えないようにするだけ
  - 家計簿の記録の一覧には、毎月の分が1件ずつは出ない（「これからのお金の動き」には出る）
- **(b) 毎月、本物の記録（家計簿の行）を自動で作る**
  - ルールから、その月が来たら家計簿の記録を作る。月ごとに金額を直せて、ルールを消しても過去の記録は残る
  - 作る仕組みが大きい（いつ・どの端末が作るか、2台で重ならないように）。口座払い（家賃など）の記録には、支出の払い方に「口座」が要る（D11 の2を変える）。お金の計算を、ルールではなく記録から数える形に変える（手順8の「お金の計算を1か所に」と同じくらいの大きさ）
- **(c) 今のまま設定に置き、編集と「やめる」だけ足す**
  - いちばん小さい。設定から入れるのは変わらない

決定: (a)（2026-10-31）
- 固定費（`fixed_costs`）に「いつから」と「いつまで」（空なら続く）を持たせる。期間の外の月は数えない。今ある固定費は「前から続いている」として扱う
- 「収支を記録」に「毎月くり返す」を足す。その日を毎月の日にして、その月から数える
- かからなくなったら「やめる」で「今月まで・先月まで」を選ぶ。過去の月は数え続ける
- 金額が変わったら「来月から金額を変える」。今のルールを今月までで終わらせ、来月からのルールを作る
- 「削除」は、まちがえて作ったときだけ（過去からも消える。「元に戻す」付き）
- 一覧は家計簿のタブの「毎月のお金」に置き、設定から外す
- 毎月の収入（固定収入 `fixed_incomes`）は、固定費の「収入」に移して1つにする（2026-10-31 に移し、空になった表は 2026-11-01 に消した）

理由:
- 今のお金の計算の考え方（ルールから毎月の分を数える）のまま、「やめたら過去の月まで消える」を直せる

## D16: 型の検査（checkJs）で、画面の要素の型をどう付けるか

D4 の手順3で TypeScript の検査（`checkJs`）を入れたら、`js/` に 336 件の間違いが出た（2026-11-02）。

- **(b) `getElementById` の結果を `any` とみなす宣言を足す**: コードは変えないが、要素まわりは検査されない
- **(c) 呼ぶ所ごとに JSDoc で型を書く**: `/** @type {HTMLInputElement} */ (document.getElementById('ldg-amount')).value`。1か所ずつが長くなる

決定: (a)。取り出し関数は、要素があるかと種類（`instanceof`）を確かめ、違えばどの id かを書いて止める。(c) は少数の特殊な要素だけに使う。(b) は使わない（2026-11-02）

作り:
- `MoneyUI.inputById`・`selectById`・`textareaById`・`dialogById`（`js/ui.js`）。`<dialog>` は `openSheet` に渡す所などが7か所あり、少数の例外とは言えないので、同じ形の関数を足した

- `.value` を使っているから全部 `<input>`、とは限らない（`<select>`・`<textarea>` もある）。置き換える前に、id ごとに HTML の中の要素の種類を調べて分けた

- `<canvas>`・`<button>`・`querySelector` で取った要素など、少数のものは (c) の JSDoc
- `strict` はまだ入れない（引数に型を書いていない所を、全部まちがいにしない）。`.ts` に移すときに見直す

理由:
- 163件あるので、共通の関数にまとめると、直すのも保ち続けるのも楽
- `any` にすると、型の検査で拾えるはずの間違いも見逃す
- 戻り値に型を書くだけでは、本当にその要素かは保証されない。あるかと種類を確かめる形にする

## D17: TypeScript のモジュールと、今のふつうの `<script>` のつなぎ方（D4 の手順4）

D4 の手順4で、計算ロジックから `.ts`（ES モジュール）に移す。画面の `js/app.js` などは、しばらくふつうの `<script>` のまま `window.MoneyCalc` などを使い続けるので、つなぎ方を決める（2026-11-02）。
モジュールはいつも HTML を読み終えてから動く。計算ロジックだけをモジュールにすると、今のままでは `js/app.js` のほうが先に動いて `MoneyCalc` が見つからない。

1. つなぎ方
- **(a) 入口のモジュール（`src/main.ts`）が計算ロジックを import して `window` に出す。ふつうの `<script>` は `<body>` に `defer` で置く**: `defer` のふつうの `<script>` とモジュールは同じ列に並び、書いた順に動く。試作で、ビルドと `npm run dev` の両方で確かめた。`<head>` に置くと、ビルドしたときだけ Vite がモジュールを `<head>` の最後に動かし、ふつうの `<script>` が先に動く
- **(b) 計算ロジックを、ふつうの `<script>` としてもう1つビルドする**: 読み込みの順は今のまま。ビルドが2つになり、`npm run dev` で `.ts` を直してもすぐには映らない
- **(c) 画面も含めて全部を一度にモジュールにする**: `onclick` から呼ぶ約230の関数を全部 `window` に出す。D4 の「少しずつ」と合わない

2. ビルドが作るファイルの名前
- **(a) 固定する（`assets/main.js`）**: `sw.js` の `ASSETS` に書くだけ。版（`CACHE_NAME`）は中身の指紋で変わる。手順6（一覧をビルドから作る）はあとで
- **(b) 指紋を付ける**: 手順6を今やる

3. `.ts` の検査の厳しさ
- **(a) `src/` の `.ts` は `strict`、`js/` は今のまま `strict` なし**
- **(b) 全部が `.ts` になるまで `strict` なし**

決定: 1(a)・2(a)・3(a)。ただし次の4点を、最初の PR（`clock`・`money`）の完了条件にする（2026-11-02。レビューで足した）
- ソースの確認とビルド成果物の確認を分ける（`assets/` はリポジトリにないので、`tests/sw.test.mjs` ではなく公開の手順で確かめる）
- 先読みの漏れを防ぐ: 出力の JS を1つに限り、Vite が作ったファイルと、出力の `index.html` が読むファイルが、すべて `ASSETS` にあることを確かめる（名前を固定しても、別のファイルが出れば漏れる）
- `js/` 用と `src/` 用の検査の設定を分け、CI で両方を検査する。`types/globals.d.ts` の `MoneyClock`・`MoneyCalc` は `src/` の export から型を取る
- 起動の順番: 出力の HTML でモジュールがふつうの `<script>` より先に並ぶことを確かめる。トップレベルの `await` は使わない（待っている間にふつうの `<script>` が先に動く）。本番と同じビルドで、起動・主要な画面・オフラインでの読み直しをブラウザで確かめる

作り:
- `.ts` は `src/` に置く。入口は `src/main.ts`。Node（テスト）と Vite の両方がそのまま読めるように、拡張子付きの import・`import type`・`erasableSyntaxOnly` にそろえる。`src/package.json` の `"type": "module"` で、Node に ES モジュールだと伝える（ルートに書くと、まだ CommonJS の形の `js/` をテストから読めなくなる）
- 型の検査: `tsconfig.json`（`js/`。`strict` なし）と `src/tsconfig.json`（`strict`）。共通の設定は `tsconfig.base.json`。`npm run typecheck` が両方を検査する
- ビルド: `vite.config.mjs` で出力の名前を `assets/main.js` に固定する。対象を ES2021 にし、トップレベルの `await` があればビルドを止める（Vite は警告だけで続けるので、`onLog` で止める）
- 公開の手順（`scripts/build-pages.sh`）: `assets/` の全ファイルと、出力の `index.html` が読むファイルが `ASSETS` にあるか、JS が1つか、モジュールが `js/` より先か、`js/` がすべて `defer` かを確かめる。どれかが違えば公開しない
- `sw.js`: `ASSETS` に `./assets/main.js` を書く。手元（`npm run dev`）には `assets/` がないので、そのときは先読みしない。キャッシュから取り出すときは `Vary` を見ない（`ignoreVary`）。ブラウザでオフラインの読み直しを試したとき、モジュールの `<script>` は `Origin` 付きで読まれ、先読みのときは `Origin` がないため、`Vary: Origin` を返すサーバーではキャッシュから読めなかった（GitHub Pages は `Vary: Accept-Encoding` だけだが、サーバーのヘッダーに頼らないようにした）

理由:
- (a) は今の画面を変えずに、計算ロジックから1つずつ移せる。手元と本番で同じ順に動く
- 名前を固定すれば `sw.js` の仕組みを変えずに済む。漏れは公開の手順で見張れる
- 計算のファイルは小さく、`strict` で全部に型を書いても無理がない。型の恩恵がいちばん大きい

## D18: 画面（`js/app.js`）を TypeScript に移すやり方（D4 の手順4の残り）

- **(a) `strict`（今の `src/` と同じ）**

## D19: 共通部分（状態・保存・同期・認証）を TypeScript に移すやり方（D18 の手順2）

`js/app-core.js` に残っているのは、状態を持つ変数（`st`・`server`・`outbox`・`currentUser` など）と、それを使う流れ（保存 → 送信待ち → 送る → 読み直す、ログイン → 起動）と、画面に出す部分（同期のバナー・ログイン画面・描き直し）。計算（行の差分・操作の作り方・送信・受け取り）は `src/data.ts` に移してある。決めること（2026-11-02）:

- 流れの途中で、画面の関数（`showSyncBanner`・`renderCurrentSection`・`renderHome`・`renderCal`・`maybeShowStartupTasks` など）を直接呼んでいる
- `js/` は `st` を約560か所、`server`・`outbox` を約50か所で使う
- Supabase のライブラリは CDN の `@2`（版を固定していない）。型は `any`

## D22: 「使えるお金」を、この先の残高の最低点にする（D11 の見直し）

背景: D11 の「給料日までに使えるお金」は、次の給料日の前日までの入出金しか見ない。給料日のあとにカードの引き落としが来る使い方（給料がほぼカード代に消える）だと、給料日の前は余裕があるように見えて、入金後に足りなくなる。「今月の収支見通し」も、収入は次の給料、固定費は今月の残り、カードは来月の引き落とし分と、数える期間が項目ごとに違い、何月の何が足りないのか読み取れなかった。

選択肢:
- **見る範囲（A）**: (1) 次の給料日の前日まで（今まで）、(2) 次のカード引き落としのあとまで、(3) この先 N 日の残高の最低点
- **今月の収支見通し（B）**: 日付順の入出金の一覧に残高を添える／「今月」に厳密にそろえた合計にする
- **記録していないカード払い（C）**: 何もしない／余裕額を上乗せ／実額と家計簿の差の平均を未確定の月に足す

決定（2026-11-05）:
1. **使えるお金**: この先 90 日の残高の見込み（今日を含む）の最低点。給料と引き落としの順番によらず、「今使っても、この先で口座が 0 を割らない上限」になる。足りないときは 0 で止めずマイナスのまま（D11 のまま）。続いている予定（今日までに始まって終わっていないもの）の予算は、さらに引く。下限は 0 円（余裕額は持たない。必要になったら設定にする）
2. **今月の収支見通し**: やめて、「これから90日のお金の動き」に置き換える。日付順に入出金を並べ、その日の終わりの残高を添え、最低点に印を付ける
3. **残高のグラフ**: 見た目はそのまま。給料・引き落としなどの動きがある日に点を打ち、最低点を色を変えた大きな点にする。点を押すと、その日の動きが出る
4. **記録していないカード払い（C）**: 何もしない。先の月ほど引き落とし額が実際より小さく出るので、90 日の最低点は先のほうほど楽観的になる。カードの確定額の入力（引き落とし前から入れられる）で、確定した月は正しくなる。差のデータが溜まったら、改めて考える

理由:
- 「来月のカードがいくらで、バイト代がいつ入るから、あといくら使える」という頭の中の計算と同じになる
- バイトが 2 つ、カードが 2 枚あっても、日付順に並べるだけで済む（合算の決まりを足さなくてよい）
- 最低点は、給料日と引き落とし日の前後関係に左右されない

D11 の「ホームでいちばん大事な数字」の決定 4 と、ホームの構成 6（今月の収支）はこの決定で置き換える。

## D23: ジムの記録（gymapp）を同じ DB に置く

背景: 姉妹アプリ [gymapp](https://github.com/Keitaro0510/gymapp)（筋トレの記録。1ファイルの PWA）は、記録が端末の `localStorage` にしかない。端末が変わる・消えると失われ、複数の端末では使えない。maney-app は DB をテーブルに分け終えたので、gymapp も関係データベースに載せ、あとで予定・お金・タスクとつなぎたい。

選択肢:
- **DB の置き場所**: (a) maney-app と同じ Supabase プロジェクト、(b) gymapp 用に別のプロジェクト
- **マイグレーションの置き場所**: (a) maney-app の `supabase/migrations/`、(b) gymapp のリポジトリ
- **gymapp の作り**: (a) 1 ファイルのまま DB をつなぐ、(b) maney-app と同じ土台（Vite・TypeScript・テスト・CI）に移す
- **作り直し構想（training-log。Next.js・FastAPI・Cloud Run の別構成）**: 進める／やめる

決定（2026-11-05）:
1. **DB は同じ Supabase プロジェクト。テーブル名は `gym_` で始める**（`gym_exercises`・`gym_workouts`・`gym_sets`。形は gymapp の `docs/PLAN.md` のたたき台から、実装のときに決める）
2. **マイグレーションは、この maney-app の `supabase/migrations/` に置く**。履歴とテストを1か所に揃える（gymapp 側には置かない）
3. **gymapp は maney-app と同じ土台に移す**。今の1ファイル版は、新しい版が確かめられるまで公開し続ける
4. **training-log は削除した**。部位・推定 1RM・停滞の検知・AI コーチの構想は、gymapp の `docs/PLAN.md` に引き継いだ

理由:
- ログインが1つで済み、あとで予定・お金・タスクと結合できる（カレンダーにトレーニングの日を出す、ジム代を1回あたりにする、など）
- 同じプロジェクトを触る入口が2か所だと、履歴が食い違いやすい
- 1ファイルの864行に DB をつなぐと、保守しにくくなる
- 別の技術構成（Cloud Run・別の DB）は、学ぶ範囲も運用する場所も増える

進め方: gymapp の `docs/PLAN.md`。この決定にかかわる maney-app 側の作業は、gym のテーブルのマイグレーション・RLS のテスト・`docs/db/SCHEMA.md` への追記（新しいテーブルを足すだけで、既存のテーブルには触れない）と、あとで maney-app の画面から gym の記録を読む連携。

実装（2026-11-05。`20261105140000_gym_tables.sql`・`supabase/tests/database/10_gym.test.sql`）:
- テーブル: `gym_exercises`（種目。消していないものの中で名前が一意、削除は `deleted_at`）・`gym_workouts`（`performed_at` と、日本時間の日 `date`）・`gym_sets`（`kg` は小数、`reps` は1以上、`rpe` は1〜10で空でもよい）。作法は ほかのテーブルと同じ（`user_id`・RLS・履歴・`position`）。トレーニングを消すときは、先にセットを消す（`on delete cascade` にはしない。`apply_op` の競合の検出を通すため）
- **毎日の写しと復元には入れる**（ジムの記録もバックアップされる）。ただし、**写しから戻すと、ジムの記録も写しの時点に戻る**。お金だけを戻したいときの手順は `docs/db/RESTORE.md`
- **JSON の読み込み（`import_backup`）には入れない**。`private.import_tables()` は、写しのテーブルから `gym_` で始まるものを除く。入れると、maney-app の読み込みのたびにジムの記録が消えるため
- `apply_op` で保存できるテーブルに3つを足し、同じ名前の種目（消していないもの）を競合（`duplicate`）として返すようにした
- ローカルでは、全マイグレーションと全 DB テストが通った（gym は42件）。本番には 2026-11-05 に適用した（Supabase MCP の `apply_migration`。バージョンはファイル名の `20261105140000` に直した。3つのテーブル・RLS・トリガー6つ・写し／読み込みの一覧・`apply_op` を確かめ、既存のテーブルの行数は変わっていない。Advisors に新しい指摘なし）

## D24: ジムの種目に部位を持たせる（gymapp #10）

背景: gymapp で、トレーニングした部位を人体図に赤く出したい（gymapp の #11）。そのために、種目ごとに「どの筋肉に効くか」を DB に持つ。

選択肢:
- **部位の持ち方**: (a) 主に使う部位1つだけ、(b) 主に使う部位1つ＋補助の部位（複数）
- **肩の分け方**: (a) 肩1つ、(b) 前部・中部・後部の3つ

決定（2026-11-05。ユーザーが選んだ）:
1. **主に使う部位1つ＋補助の部位（複数）**で持つ（`gym_exercises.primary_muscle`・`secondary_muscles`）
2. **肩は前部・中部・後部に分ける**（サイドレイズ=中部、プレス=前部で、効く場所が違う）
3. 部位は14: `chest` 胸 / `delt_front` 肩（前部）/ `delt_side` 肩（中部）/ `delt_rear` 肩（後部）/ `lats` 広背筋 / `upper_back` 僧帽筋・菱形筋 / `biceps` 上腕二頭筋 / `triceps` 上腕三頭筋 / `forearm` 前腕 / `abs` 腹 / `glutes` 臀部 / `quads` 大腿四頭筋 / `hamstrings` ハムストリング / `calves` ふくらはぎ
4. 部位は**任意**。未設定の種目は、空のまま使える（人体図には出さない）

理由:
- 補助の部位があると、ベンチプレスで肩の前部・上腕三頭筋にも負荷がかかる、という現実に近い表示になる
- 肩を分けないと、サイドレイズとプレスの違いが人体図に出ない
- 部位が必須だと、新しい種目を足すたびに止まる

- テーブルを足すのではなく列を足すだけなので、毎日の写し・`apply_op`・復元は変えていない（どれも列を名前で扱う。部位のない古い写しから戻すときは、足りない列は既定値になる）
- 部位の一覧を増やすときは、新しいマイグレーションで `check` を作り直す（`check` から `private` の関数は呼べないため、配列を直接書いている）
- 今ある種目への割り当て（値の入力）は、マイグレーションには入れず、本番に別に書き込む。割り当て表は gymapp の #10
- ローカルでは、全マイグレーションと全 DB テストが通った（gym の部位は14件）
- 本番には 2026-11-05 に適用した（Supabase MCP の `apply_migration`。バージョンはファイル名の `20261105170000` に直した）。そのあと、本番の今の種目（39。ユーザーの種目の名前を正式な名称に直し、足や背中などの主要な種目を足したもの）すべてに、標準の割り当てを入れた（未設定 0。ジムの記録は 40回・775セットのまま）。割り当ては gymapp の `src/muscles.ts`（`DEFAULT_PARTS`）
